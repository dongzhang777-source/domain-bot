## 二、四条开跑前阻断项

每条统一给四件事：**现象 / 证据 / 为什么现有复审机制发现不了 / 触发哪条判据**。这四条的共同特征是——**判定线签字后就修不了**（criteria 明定「生效后探针期内不得修改」），所以它们的修复窗口就是现在。

### 2.1 归档枯竭：稳态每天约 3 条候选，末轮已经是 0 → 触发 I-1

**现象**：轮1 `candidates=647` → 轮2（29 秒后）`=1` → 轮3 `=3` → 轮4 `=0`。

**证据**：`memory/observations.jsonl` 四行原文（§1.3 表）；`src/index.ts:119` `store.recordItems(candidates, now)`（全量候选入档，配额截断前的 647/341 条全部写进归档）；`src/memory/store.ts:131-159` `recordItems` 实现；`src/collector/dedupe.ts:39-55` `dedupe` 用 `knownIds` 精确屏蔽已入档条目；`memory/archive.json` 实测 651 条 / pushed 仅 10 条。

**因果链闭合**：`scoreThreshold=0.45`（`config/domain.json`，四个 commit 从未变过）在 sqrt 压缩后的公式（`src/refinery/scorer.ts:32`）下，通过率是 **3/341 = 0.88%**。轮3 那 3 条过阈值的候选被全量入档 → 轮4 的 relevant 从 341 掉到 338（正好少 3）、candidates 掉到 0。**过阈值的就是那 3 条，没有第二批。**

**这是 S13 的修复直接造成的**。矩阵 S13（`cross-review-matrix-2026-09-01.md:83`）原文：「**归档只存被推送条目**，未推送的 ~954 条每轮重评」，A/C 双方共识，A 并指出「LLM 接入后是重复烧钱」。A3 按此修为全量入档——**修掉了「每轮重评烧钱」，代价是把「每轮都有候选」变成了「候选一次性耗尽」**。旧行为下那 3 条会每轮重评（传送带，但不会枯竭）；新行为下它们进归档就再也不回来。

**为什么现有复审发现不了**：A3 的验收判据是「字段测试 + 真实一轮数据」（`workplan` Phase A 表）。**一轮**看不出枯竭——枯竭需要连续 2–4 轮才显形，而验收只跑一轮。D 的 §303 估「稳态下每天新增候选是个位数到几十」，方向对但**量级高了一个数量级**（实测约 3 条/天），且没有把它列为阻断项。

**触发判据**：I-1「连续 3 轮 candidates=0」→ 判「探针无效」。按每天 1 轮，只需连续 3 天 feed 无新增相关内容（周末 / 节假日 / arXiv 更新节奏）即触发。**而末轮已经是 0，即已走到 1/3。**

### 2.2 Phase D 的运行方式与反馈接收的启动条件互斥 → 触发 I-2 + 废掉 P-2

**现象**：按 workplan 写的方式跑两周，`feedback.json` 永远不会产生一个字节。

**证据链**：

| 环节 | 位置 | 内容 |
|---|---|---|
| 计划的运行方式 | `docs/workplan-2026-09-02.md` Phase D | 「每天 1 轮（**`npm start`**，cron/launchd 托管方式待定）」 |
| `npm start` 的实际含义 | `package.json:11` | `npm run build && node dist/index.js **--once**` |
| 反馈接收的启动条件 | `src/index.ts:247` | `if (telegram && **!once**)` → `--once` 模式**必然跳过** |
| 接收端必须常驻 | `src/feedback/receiver.ts:76-92` | `pollFeedback` 是 `for (;;)` 长轮询（`:81`），`timeout: 30`（`:68`），返回 `Promise<never>` |
| 日志给出的承诺 | `src/index.ts:253` | 「本轮的 👍/👎 将在**下次常驻运行**时入账」 |

**cron + `npm start` 模式下永远没有「下次常驻运行」**——每次进程跑完一轮就退出，Telegram 回调无人接收；24 小时后的回调被 Telegram 丢弃。

**这是一次转录损耗，而且有原文对照**：`cross-review-fourparty-2026-09-02.md:101` 的 Phase D 原文是「每日 cron 触发 `--once`（**或常驻 + 长轮询**）」——**两个分支都在**。`workplan-2026-09-02.md` 转录时只抄了第一个分支，把唯一可行的第二个丢了，还补了一句「托管方式待定」把风险延后。而同一份四方汇总文档的 `:37` X4 恰恰在警告：「**转录损耗不挑人**」（原话是对着执行者手抄错 observations 两字段说的）。

**为什么现有复审发现不了**：这是本报告新增的**第 5 类断开路径**。D 在 `review-2026-09-02-external.md:85-90` 列了四类「绿灯但断开」：链级（函数无调用者）、进程级（store 快照陈旧）、配置级（`process.argv[1].endsWith('index.js')`）、语义级（α 步长小于浮点噪声）。**四类都在代码里**，而这一条在**代码与运行计划的接缝上**——代码是对的（常驻模式确实会启动接收），计划是错的（选了不常驻的模式），任何只读代码的审查看不见它。本报告称之为 **launch-mode 级（运行方式级）**。

**更要紧的是：A2 的守卫把这个缺陷锁死了。** `tests/wiring.test.ts:71-73`：

```ts
it('常驻分支的启动条件必须包含 telegram 判定（无 token 不该崩，有 token 不该跳过）', () => {
  expect(mainBody).toMatch(/telegram\s*&&\s*!once/)
})
```

测试名写「**有 token 不该跳过**」，而断言的文本 `telegram && !once` 的语义恰恰是「**`--once` 时必然跳过**」。这条守卫是 A2 按 D 的 V2 变异测试（把条件改成 `if (false)`，67 个测试无一红）加的，它确实能防住那个变异；**但它同时把 `!once` 写成了必须存在的契约——任何让 `--once` 也接收反馈的修复，都会让这条测试变红。**

而 D 的 V3（`:72-84`）批评的正是「守卫本身是文本存在性检查，不是可达性检查」，并列表指出 `if (false) updateWeights(a, b)` 会**判绿**。**A2 的修复方式恰好又是文本存在性检查**，而且这次更糟：D 的例子里「文本存在但永不执行」是漏判，而这里是**断言了一段永不执行的分支条件必须存在**——把缺陷升格成了规格。

**锁定不止一层：还有一个运行时测试，把这个缺陷盖上了「与生产行为一致」的章。** `tests/startup.test.ts:37-47`（本报告初稿漏引此文件，是 2026-09-02 16:31 实跑 `npm test` 时才从测试名里发现的）：

```ts
it('--once 模式不启动反馈接收（与生产行为一致）', async () => {   // :37
  ...
  await startBot({ ..., telegram: { token: 't', chatId: 'c' }, once: true, ... })
  expect(pollCalled).toBe(false)                                  // :46
})
```

它与紧邻的 `:25-35`（「常驻 + 有 telegram 时，`startBot` 必须**真的调用** `pollFeedback`（不只是文本存在）」，断言 `pollCalled).toBe(true)`）构成一对。这一对说明**写测试的人完全清楚常驻与 `--once` 的差别，是刻意把「`--once` 不接收反馈」编码为正确行为的**——而且测试名里的「**与生产行为一致**」把一个运行方式缺陷表述成了生产事实。

于是 §2.2 这条缺陷被**两层独立守卫**锁死，且两层性质不同：

| 层 | 出处 | 断言形式 | 修复时会怎样 |
|---|---|---|---|
| **文本层** | `tests/wiring.test.ts:71-73` | `expect(mainBody).toMatch(/telegram\s*&&\s*!once/)`——源码里必须存在这段文本 | 改掉 `index.ts:247` 的条件 → **红** |
| **运行时层** | `tests/startup.test.ts:37-47` | `expect(pollCalled).toBe(false)`——真实调用 `startBot({once: true})` 后断言接收端未被启动 | 让 `--once` 也启动接收 → **红** |

**这比「一条守卫写错了」严重**：文本层被 D 的 V3 提前批评过，容易被当成已知问题；运行时层看起来是**正经的行为测试**（真调函数、真断言副作用，正是 `cross-review-fourparty:115`「生产级验收三件套」要的东西），**它形式上完全合格，合格的形式恰恰是它更难被质疑的原因**。A′2 必须同时处置这两处，否则修复者会被第二道红灯挡回来、并很可能据此认为「修复方向错了」（详 §七 A′2）。

**触发判据**：I-2「反馈率 < 5% 判探针无效」（实测已是 0%）；P-2「👍率 ≥30% 且有效反馈 ≥20 条」永远拿不到分母。**两周后写出的结论会是「用户不给反馈」，而真相是「按计划的方式跑，系统根本没在听」——这正是 D 硬阻断 1 描述的「假阴性，且事后不可辨」，只是成因从 V1（store 陈旧）换成了运行方式。**

### 2.3 G-1/P-1 证据链断：头号判据既禁止手抄、又无脚本读数 → 无法判定

**现象**：判定线最重要的那条指标（主动查看次数）在当前工具链下**读不出来**。

**证据**：三条规则叠加成一个死结——

| 规则 | 出处 | 原文要点 |
|---|---|---|
| viewed 的唯一定义 | `docs/probe-verdict-criteria.md` §2c | 「**viewed 的唯一定义 = `views.json` 中该 digestId 的记录存在**」；「文件版（outbox/*.md）**不计 viewed**」 |
| 判定数据的唯一来源 | 同上 §4 | 「所有判定数据以 `scripts/gen-evidence.mjs` 产出为准（observations.jsonl + feedback.json + weights.json），**禁止手抄**」 |
| 脚本的实际读取范围 | `scripts/gen-evidence.mjs:10-16` | 读 `observations.jsonl`、`archive.json`、`feedback.json`、`weights.json` —— **不读 `views.json`** |

§4 那条规则括号里列的三个文件，正好就是脚本读的那三个；**`views.json` 是 agy 三审之后才加的机制**（`7f08ab8`，09-01 21:38，晚于判定线首稿 `2ae4b5c` 21:06 与 §4 规则的定稿 `8d17d13` 21:18），加的时候没有回头同步 A7 的脚本。

**结果**：G-1（放弃线）与 P-1（通过线）都建立在 viewed 计数上，G-3/P-3（戒断测试）也依赖它。**四条判据共用一个读不出来的数**。而 criteria 又明定不许手抄——于是「不许手抄」这条防转录损耗的纪律，与「脚本没跟上」这个实现缺口叠加，**把头号判据变成了不可判定项**。

**为什么现有复审发现不了**：`gen-evidence.mjs` 是 A7 的产物，验收判据是「脚本可复跑」——它确实可复跑，输出也确实来自 artifacts。**验收对照的是「有没有脚本」，不是「脚本覆盖不覆盖判定线的全部判据」。**

### 2.4 I-4 死判据：改口径时把 0.99 阈值原样搬运，而新口径下实测最高分 0.604

**现象**：「打分器失效」的唯一自动判据永久沉默。

**证据（两个 commit，间隔 74 分钟）**：

| 时刻 | commit | 内容 | 0.99 在新口径下可达吗 |
|---|---|---|---|
| 09-01 **19:52:27** | `2c03e6b` | 标题原文：「sqrt 压缩破解打分饱和——arXiv 类摘要从恒 1.000 降到 **0.946**，四档可区分」 | — |
| 09-01 **20:03:40** | `df17047` | `saturationRate` 首次落盘：`candidates.filter(c => c.valueScore >= 0.99)`，注释写「持续 > 0.5 说明打分器又饱和了」。**此时算的是加权×新颖性分** | ✅ 可达——`applySourceWeight` 乘数是 `0.5 + w`（`evolve.ts:33`），值域可 >1，加权分够得着 0.99 |
| 09-01 **20:59:15** | `a1bd817` | A3 按 D 盲区3 改口径。diff 只改了两处：注释加「（D 指出：用加权分算时，学习越成功误报越凶）」、过滤对象 `c.valueScore` → `rs`（原始分）。**`>= 0.99` 这个数字原样搬运，未被触碰** | ❌ **从这里开始不可达**——原始分值域 `[0.25, 1.0]`，实测最高 0.946 |
| 09-01 **21:06** | `2ae4b5c` | 判定线草稿落盘（**7 分钟后**），I-4 定为「`saturationRate` 持续 > 0.5（**原始分口径**）」 | ❌ 死判据正式入册，且 `criteria:3` 明定生效后不得修改 |
| — | `src/memory/observe.ts:36-37,73-75` | `saturationRate` = 候选中**原始分 >= 0.99** 的比例 | — |
| — | `src/refinery/scorer.ts:30-32` | `valueScore = 0.25 + 0.5·min(1, √k/√8) + 0.25·min(1, √s/√6)` | — |

**算术（先把话说准：单条不是「数学上不可达」）**：要 `valueScore >= 0.99`，需 `0.5·kwPart + 0.25·sigPart >= 0.74`，而两项上限之和恰为 `0.5 + 0.25 = 0.75` → **必须 `kwPart ≈ 1` 且 `sigPart ≈ 1`，即同时命中 ≥8 个领域关键词与 ≥6 个信号词**。穷举 `config/domain.json` 的 23 关键词 × 10 信号词，达标的整数组合有 **80 种**，最小的就是 `(k=8, s=6)`，其值恰为 `1.0`。**所以「0.99 超出公式值域」是错的，值域上限就是 1.0**——本报告初稿这样写过，已在 §8.4 第 4 条撤回。

**但判据要的从来不是「有一条达标」，而是「过半候选达标」**。`observe.ts:73-74` 的定义是 `count(rs >= 0.99) / count(rs)`，I-4（`criteria:20`）的触发条件是它**持续 > 0.5**。于是真正的门槛是：候选池里**超过一半**的条目，每一条都要同时命中 ≥8 个关键词与 ≥6 个信号词。

**实测（`memory/observations.jsonl` 第 3 轮，唯一带原始分字段的一轮）**：`rawTop1 = 0.604`、`rawP50 = 0.5`、`saturationRate = 0`。也就是**整个候选池里最好的那一条，距单条达标线还差 0.386**；要让过半条目跨过它，分布需整体右移约 0.39——而这批条目已经通过了 `scoreThreshold = 0.45` 的筛选，是打分器认为最相关的一批。4 轮 `saturationRate` **恒 0**，651 条归档无一例外。

**`0.946` 这个数可以反解**：`f(7, 5) = 0.25 + 0.5·√7/√8 + 0.25·√5/√6 = 0.9459`。`2c03e6b` 标题里那个「arXiv 类摘要（最长、关键词最密集的一类）降到 0.946」，对应的正是 **7 个关键词 + 5 个信号词**，距达标的 `(8, 6)` 各差一个。**修复者当时已经把最好的一类语料推到了达标线的紧邻位置，而这个数就写在他自己 67 分钟后要被搬运阈值的那次提交的上一条 commit 标题里。**

> **也就是说：I-4 的死刑判决书，写在它诞生前 67 分钟的 commit 标题里。** 改口径的人只要抬头看一眼当天早些时候的提交记录，就能发现 0.99 这个数字在原始分口径下够不着。

**这条为什么特别值得写**：它活过了两轮审查。D 的盲区 3（`review-2026-09-02-external.md:174`）指出「`saturationRate` 用加权分算，学习越成功误报越凶」——**方向完全正确**，A3 照此改到原始分口径；四方汇总把它提炼成 X2「观测仪器必须与『你声称在测的东西』同构，两轮都栽在指标不测它声称测的维度」。**但改口径的时候没有人算一次「原始分口径下 0.99 是否可达」，总结 X2 的时候也没有人回头检查现存的判据**。于是：修掉了「误报」（加权分可 >1 导致虚高），造出了「永不报」（原始分上限 0.946）。

**触发判据**：I-4 是判定线里唯一用来识别「打分器失效」的自动闸。**它失效意味着：如果打分器真的坏了（比如关键词表被误改、阈值漂移），探针不会判「无效」，而是会把坏仪器的读数当成需求信号一路带进结论。** 这比判据缺失更危险——缺失会被发现，沉默不会。

### 2.5 由四条阻断项提炼的新超共识 X6

续 `cross-review-fourparty-2026-09-02.md:32-38` 的 X1–X5：

> **X6：修复的验收只对照「原缺陷清单」，不对照「修复后的系统状态」，于是每一项修复都能制造一个不在清单上的新阻断项，而复审机制在结构上发现不了它——因为复审的对象是「清单是否执行完毕」，不是「执行之后系统变成了什么」。**

本轮四个实例（全部可复核）：

| 修复 | 原缺陷 | 制造的新阻断 | 复审为何漏 |
|---|---|---|---|
| A3 `recordItems(candidates)` | S13 未推送条目每轮重评、LLM 重复烧钱 | §2.1 候选池枯竭 → I-1 | 验收只跑**一轮**，枯竭需 2–4 轮才显形 |
| A3 `saturationRate` 改原始分 | D 盲区3 加权分自证污染 | §2.4 I-4 实测不可达（阈值 0.99 原样搬运） | 改口径时只复核了「口径对不对」，没复核「阈值在新口径下还成不成立」 |
| A7 `gen-evidence.mjs` | X4 手抄转录损耗 | §2.3 G-1/P-1 无脚本读数 | 验收判据是「可复跑」，不是「覆盖全部判据」 |
| A2 启动链守卫 | D-V2 摘掉 pollFeedback 67 测试不红 | §2.2 守卫把 `!once` 缺陷固化为契约 | 守卫本身是文本检查（D-V3 已批评过这一点） |

**X6 与 X1/X2 的关系**：X1 说「测试绿 ≠ 系统通，换一层还会复发」，X2 说「指标不测它声称测的维度」。X6 是它们的**上游成因**——之所以换一层就复发、之所以指标跑偏，是因为验收的参照物始终是**上一轮的缺陷清单**，而不是**这一轮修复后的完整系统状态**。清单是有限的，系统状态是无限的。

**可操作的对策（写进 §七 工单验收纪律）**：每个修复的验收判据必须包含一条「**修复后系统状态断言**」，而不只是「原缺陷不复现」。具体形态：
- 涉及归档/去重的修复 → 必须连跑 **≥4 轮**并贴 `observations.jsonl` 全文，不接受单轮
- 涉及观测指标的修复 → 必须附**该指标的值域计算 + 实测分布**（公式最小值、最大值、判据阈值是否落在值域内，**以及当前 artifacts 上的 P50/Top1**）。**只算值域不够**——本报告初稿就是只算了值域，才把 I-4 误写成「数学上不可达」，实际值域上限是 1.0、真正的判死依据是实测分布（§8.4 第 4 条）
- 涉及证据脚本的修复 → 必须附**判据覆盖对照表**（判定线每一项判据 → 脚本输出的哪个字段）
- 涉及守卫测试的修复 → 必须回答「**这条守卫断言的文本，如果按它的字面语义执行，系统行为是什么**」

## 三、五条会让读数失真的缺陷（不阻断开跑，但会污染结论）

与 §二 的区别：这五条不会让探针停下来，**会让它跑完两周、给出一份看起来完整、实际上系统性偏移的读数**。其中 3.1 是被测试锁定的刻意设计，本报告不指控为 bug。

### 3.1 零反馈下人工先验双向收敛——先说清楚这不是 bug

**公平声明（必须先讲）**：「无反馈的源向 0.5 回归」是**刻意设计，且被测试显式锁定**：

- `src/memory/evolve.ts:16` 注释原文：「源权重向后验均值缓慢移动（α 步长）。**0 反馈的源保持在 0.5 附近，不会被误杀**。」
- `tests/evolve.test.ts:24-31` 测试名：「权重向反馈均值缓慢移动，**无反馈源缓慢回归 0.5 先验（不误杀）**」，断言 `expect(next.noisy).toBeCloseTo(0.42, 10)`，注释写「w = 0.8\*0.4 + 0.2\*0.5 = 0.42，**向先验温和回归而非冻结**」
- `src/memory/evolve.ts:12-14` `sourceValue({up:0,down:0}) = (0+1)/(0+0+2) = 0.5`，即 Beta(1,1) 先验均值

**设计理由成立**：一个人工判为低质的源，若永远拿不到反馈，就该慢慢回到中性，给它重新证明自己的机会——否则人工偏见会被永久固化，这与「自进化」的立意相反。

**本报告要报的是它的累积后果未被评估过**，三点：

**① 收敛是双向的，人工上限同样被拆。** `src/memory/evolve.ts:26` `next = 0.8·w + 0.2·0.5`。实测 `memory/weights.json` 的 7 个源权重与该公式 **100% 吻合，零例外**：

| 源 | `config` 先验 | 实测权重 | `0.8w + 0.2×0.5` |
|---|---|---|---|
| arxiv-cs-ai / huggingface-blog / github-new-llm-tools | 0.5 | 0.5 | 0.5 |
| exa-llm-news | **0.6** | 0.58 | 0.58 |
| hf-daily-papers | **0.6** | 0.58 | 0.58 |
| v2ex-hot | **0.2** | 0.26 | 0.26 |
| bili-llm | **0.2** | 0.26 | 0.26 |

而 `memory/feedback.json` **不存在**、`feedbackHash` = `sha256("[]")` → **这些变动与反馈零关系，纯粹是零反馈下的一步回归**。`src/memory/weights.ts:16` 注释知道这个问题（「避免每轮向 0.5 回归冲淡已学信号」），但闸门只防**频率**（`:23` 哈希未变则原样返回），不防**方向**——哈希一变，18 个源全体向 0.5 走一步，不管它们有没有拿到反馈。

**② 两周后人工先验只剩 6.9%。** D 在 `review-2026-09-02-external.md:303-305` 算过：每天推 6 条 × 14 天 ≈ 84 条推送，7 源分下来**每源约 12 次反馈**。每一次反馈内容变更都会打开闸门、触发一次全体回归。12 次之后：

```
0.8^12 = 0.0687  →  人工先验的权重只剩 6.9%，93.1% 来自 0.5 中性值
```

**③ 于是 §六 Q4 的结论比 D 的更强**：D 说「两周数据无法区分『用户真的偏好某源』与『随机波动』」（±0.15）；本报告补一层——**不仅学不出信号，连人工先验也会被抹除。两周后 `weights.json` 的状态约等于全 0.5，即「没有权重」**。而 `src/memory/evolve.ts:32-34` `applySourceWeight(v, w) = v × (0.5 + w)`，全 0.5 时乘数恒为 0.75 → **源权重对排序完全失去分辨力**。

> **一个反直觉的当前状态**：11 个 09-02 新入册的源，因为 `feedbackHash` 未变（闸门关闭，`weights.ts:23` 直接 `return current`），反而**完整保住了人工先验**（`:21` `state.weights[s.id] ?? s.weight`）；而 7 个老源的先验已被抹平一步。**先入册的源受罚，后入册的源幸免**——这与设计意图恰好相反。

**建议（不推翻设计，只加护栏）**：给回归设一个「先验地板/天花板」——零反馈源的权重不得越过其 `config` 先验与 0.5 之间的中点；或把 α 与反馈量挂钩（无反馈的源 α→0）。**这条须老张裁，因为它改的是 `evolve.test.ts:24-31` 锁定的语义**（列 §七 决策点 3）。

### 3.2 5 份 digest 的反馈永久不可归因（已发生的真实数据损失）

**现象**：`outbox/` 有 8 份 digest，但只有 3 份能接受反馈。

**证据**：`memory/archive.json` 的 `digestRefs` 实测 **10 个键，只覆盖 3 个 digestId**：

| digestId | ref 键数 | outbox 文件时刻 |
|---|---|---|
| `mtjc5yyi` | 6（`:0`–`:5`） | 09-01 20:06 |
| `mtjc6lvb` | 1（`:0`） | 09-01 20:07 |
| `mtje6psd` | 3（`:0`–`:2`） | 09-01 21:03 |
| `mtj8elt8` / `mtj8rdof` / `mtj8rs42` / `mtj8s2ec` / `mtj8wzm8` | **0** | 09-01 18:21–18:35 |

### 3.3 簇级 ref 只登记首条 → 源权重学习的富者愈富闭环

**证据**：`src/index.ts:122` `store.registerDigestRef(cluster.ref, digestId, cluster.items[0].id, cluster.items[0].source)` —— **只登记簇内第 0 条的 source**。而 `src/refinery/cluster.ts:29-32` 的摘要文案明写「（另有 ${group.length - 1} 条同主题来源）」，即一个簇可以含多源报道。

**后果**：用户对一簇点 👍，反馈只归给代表条目的源；**簇内其他源（可能是同一事件的更好来源）拿不到任何信号**。

**而代表位不是中立的**：`cluster.ts:9` 按 `valueScore` 降序排序后取 `group[0]`，而 `valueScore` 在 `src/index.ts:87-91` 已经乘过 `applySourceWeight(raw, weight)`（`evolve.ts:32-34`，权重越高乘数越大）。于是形成闭环：

```
权重高 → 加权分高 → 更容易当簇代表 → 反馈只归给它 → 权重更高
```

**这与 `src/memory/observe.ts:32` 已警惕的问题同源，但只防了一半**。该处注释原文：「权重上升会推高加权 P50 造成『进化生效』的**闭环自证**——判定进化只看原始分」，A3 据此把 P50/top1/saturation 全改到原始分口径。**观测口径防住了，归因口径没防**：`observe.ts` 记的 `weights` 与 `bySource` 仍然是被这个闭环推动的结果。

**探针期内的实际影响有限**（实测 651 条 `hitCount` 全为 1、`isNewRate` 轮3=1，说明聚类与去重路径在真实数据上从未触发，簇内多源的情况一次都没出现过），**但一旦中文源接通（§六 Q2）或归档重置后跑起来，这条闭环就会启动**——而它是**不可观测的**：没有任何字段记录「这条反馈归给了代表，而簇内还有 N 个源被忽略」。

## 四、九条工程欠账（与探针有效性无关的代码级缺陷）

这些不影响两周判定，但影响 domain-bot 作为**资产**被 fati-server 或 tuna 收编时的可用性（§六 Q1）。按严重度排序。

### 4.1 SSRF 防护加错了路径（最重的一条）

**实测防护覆盖面**：`grep -rn "isPublicHttpsUrl" src/` → 定义 1 处 + 调用 **2 处，全在 jina**：

| 适配器 | 是否校验 | 实际请求对象 | 能否打到本地内网 |
|---|---|---|---|
| `src/collector/adapters/agentreach.ts:204`（`fetchJinaViaExa`） | ✅ | `mcporter call exa.web_fetch_exa`（第三方） | ❌ 不能 |
| `src/collector/adapters/agentreach.ts:217`（`fetchJina`） | ✅ | `https://r.jina.ai/${source.url}`（第三方中转） | ❌ 不能 |
| **`src/collector/adapters/rss.ts:38`** | ❌ **零校验** | `withSizeLimit(fetchFn, source.url)` —— **直接 fetch 配置里的任意 URL** | ✅ **能** |
| **`src/collector/adapters/github.ts:8`** | ❌ **零校验** | 同上 | ✅ **能** |

**防护加在了经第三方中转、打不到内网的路径上；真正直接 fetch 任意配置 URL 的两个适配器零防护。**

**根因是权衡，不是疏漏**——`config/sources.json` 里 `arxiv-cs-ai` 的 url 是 **`http://export.arxiv.org/rss/cs.AI`**（HTTP，非 HTTPS），而 `fetchUtil.ts:91` 的 `isPublicHttpsUrl` 第一条就是 `if (parsed.protocol !== 'https:') return false`。**给 rss 加上这个校验，会当场拒收贡献了归档 85.6%（557/651）的主力源。** 所以「rss 不校验」在当前配置下是必然选择，只是这个取舍从未被写下来。

**低成本修法**（两案，须老张选，列 §七 决策点 5）：
- 案 A：把 arXiv 换成 https 端点（`https://export.arxiv.org/rss/cs.AI`）——**该端点是否可用需联网核实，本报告不作结论**；可用则 rss/github 直接补校验，零功能损失
- 案 B：保留 http，但给 `isPublicHttpsUrl` 加协议白名单参数（rss 允许 http+https，仍拒私网 host）

**与 agy-R1 结论的范围性分歧（附公平说明）**：`.verify-logs/2026-09-02-sourceexp/2026-09-02-domainbot-sourceexp-review-agy.md:23` 写「**P0 安全性与正确性完全达标**：`fetchJina` 重试链中，SSRF 检查严格前置于任何抓取尝试……**不存在私网探测或云元数据绕过路径**」。

**这不是审查者失职**：该轮审查对象是 commit `437365c`（信源扩展），`rss.ts` 与 `github.ts` 本轮未变更，按 commit 范围审查的方法论天然看不见跨文件的防护面不一致。**这恰好是 X6 的又一实例——复审对照的是「本轮改了什么」，不是「改完之后整个系统处于什么状态」。** 另可对照四方汇总 `cross-review-fourparty-2026-09-02.md:67` 给 B 型通道的派单结论「做架构推演可以、做数据陈述必须抽查」——本报告即是一次抽查，且结论是**该断言的范围需要收窄，内容不需要撤回**。

### 4.2 `isPublicHttpsUrl` 自身的绕过面（即使补到 rss 也不够）

`src/collector/adapters/fetchUtil.ts:84-99` **不做 DNS 解析**，只按字面 host 判断：

| 绕过形式 | 示例 | 为什么通过 |
|---|---|---|
| 十进制整数 IP | `https://2130706433/`（= 127.0.0.1） | `:76` 的正则 `^\d+\.\d+\.\d+\.\d+$` 要求点分四段，无点则不匹配；`:77` 的 `startsWith('127.')` 也不匹配 |
| 十六进制 IP | `https://0x7f000001/` | 同上 |
| IPv6 映射地址 | `https://[::ffff:127.0.0.1]/` | `:75` 只拦 `::1` 与 `[::1]` 两个字面量 |
| 八进制写法 | `https://0177.0.0.1/` | `:60` `Number('0177') = 177`，`isPrivateIPv4` 判 `a===127` 为假 |
| DNS 指向内网的公网域名 | 攻击者自有域名解析到 `169.254.169.254` | 无解析步骤，`:96` 的元数据地址黑名单只比对字面 host |

**威胁模型评估（避免夸大）**：`source.url` 全部来自 `config/sources.json`，由老张手工维护，不是用户输入 → **当前攻击面低**。真实风险场景有两个：① 未来把源注册表开放给 bot 自助添加（§六 Q1 的收编路径）；② RSS feed 内容里的链接被二次 fetch（当前代码不这样做，但收编后可能）。**因此本条列为「收编前必修」，不是「探针期必修」。**

### 4.3 `isNovel` 的 O(N) 与 `maxEntries=20000` 组合

`src/memory/store.ts:117-128`：每个候选遍历**全部**归档条目做 jaccard，`:120-124` 有 `tokenCache` 但**无上限**（`:40` `private tokenCache = new Map<string, Set<string>>()`）。

`src/memory/store.ts:30-32` 注释：「全量候选入归档后量级从『每轮≤6』升到『每轮数百』；**2 万条 ≈ 5MB JSON，两周探针够用**」，`DEFAULT_MAX_ENTRIES = 20000`。

**量级**：满档时每轮 341 候选 × 20000 归档 = **682 万次 jaccard**。这是矩阵 S12 的量化更新——S12（`cross-review-matrix-2026-09-01.md:82`）原估「归档 2000 × 候选 960 ≈ 190 万次」（A 与 B 独立算出 190/192 万，数字吻合），**但归档上限后来定为 20000，即 S12 的量级比原估算高约 3.6 倍**，而 P2-5 的处置是「🟢 可以改（探针期可选）：倒排索引或 MinHash/LSH 预筛」。

**A1 修复加剧了它**：`src/feedback/receiver.ts:20` 注释「接收端只持有目录，不持有 store——**每次回调从盘重建**」，`:36` 与 `:43` 各 `new MemoryStore(...)` → **每次回调都重读 234 KB 归档并清空 `tokenCache`**。这是 V1 的正确修法（消除陈旧快照），代价是缓存局部性归零。

**探针期内不构成阻断**（实测 4 轮总耗时约 70 分钟含人工间隔，单轮采集 1676 条可在分钟内完成），但收编到 fati-server 的多 bot 场景后会成为热点。

### 4.4 条目 id 生成口径不一致 → jina 源精确去重必然失效

`src/collector/dedupe.ts:27-29` `contentHash(item) = sha1(normalizeText(title + ' ' + body))`，而各适配器传给 `body` 的东西**不是同一类语义**：

| 适配器 | `contentHash` 的 body 实参 | 稳定性 |
|---|---|---|
| `agentreach.ts:42`（exa） | `url` | ✅ 稳定 |
| `agentreach.ts:79`（v2ex） | `t.url` | ✅ 稳定 |
| `agentreach.ts:93`（bili） | `cur.bvid` | ✅ 稳定 |
| `agentreach.ts:170`（ytsearch） | `url` | ✅ 稳定 |
| `rss.ts:61`（rss/atom） | **真实正文** `description/summary` | ⚠️ 正文改动即换 id |

## 六、四问逐答（按老张选定的「仪器有效性优先」，本节次于 §一–§五）

四问沿用老张对 fati-server 提的原问，但 domain-bot 的语境不同，**每问的答案判据也不同**。

### Q1｜整体架构和功能如何改进以实现设计目标

**先钉住设计目标**——`README.md:3-4` 原文：

> 定位：fati-server 千 bot 工厂「需求 50」命题的**假门测试探针**，第一个用户是老张本人。**一个 bot 跑通 = 无数 bot 可跑通的最小证据。**

**所以 domain-bot 的设计目标不是「成为一个好用的产品」，而是「给出一个可信的需求判定」。** 这一句决定了本问的全部答案判据：架构改进的唯一标准是**能不能给出可信读数**，而不是功能多不多、代码优不优雅。这也正是老张选定「仪器有效性优先」的理由。

按这个判据，架构分三层，**当前只有第一层没做好，后两层不该现在动**：

| 层 | 内容 | 当前状态 | 该不该现在动 |
|---|---|---|---|
| **① 仪器层** | 采集 → 打分 → 推送 → 反馈 → 观测 → 判定 | ❌ **11 项判据里 5 项无读数、4 条开跑前阻断项** | **必须现在动**（签字后修不了） |

**免登录优先纪律已在 README 与代码里落实**（`README.md:18`「需登录态的 Twitter/Reddit/小红书通道**刻意不进**无人值守管线（封号风险）」、`agentreach.ts:13` 同旨注释）——这条是 A4 的共识（矩阵 S4，三方一致），**本报告复核为已遵守，无需改动**。

### Q3｜如何改进算法，迎合用户需求

**与 fati-server 的结论同构，但缺口位置不同。** fati-server 报告 D 的判断是「算法不缺聪明，缺食物和出口」；domain-bot 的**出口是通的**（推送链路 `index.ts:139-156` 完整，8 份 digest 实证落盘），**缺的只有食物**（反馈零数据）。

**正确顺序（不可跳步，前两步是 §二 的阻断项）**：

| 步 | 动作 | 为什么不能跳 | 对应 |
|---|---|---|---|
| 1 | **让反馈能进来**：常驻运行 + `.env` 三 key 到位 | 不接，后面全是自我对弈 | §2.2 / D 硬阻断 2、3 |
| 2 | **让候选池不枯竭**：归档策略或阈值重标定 | 无候选 = 无推送 = 无反馈 | §2.1 |
| 3 | **让读数可信**：证据脚本覆盖全部判据 + I-4 重定阈值 | 否则两周后无法判定 | §2.3 / §2.4 |
| 4 | **去掉系统性偏倚**：长度归一化（D-P1，唯一未动项） | 否则结论会偏成「要长文摘要型 bot」 | §3.5② / X5 |
| 5 | **补时效维度**：`publishedAt` 入档 + 衰减因子 | 当前「旧闻降权」只能降重复、降不了陈旧 | §4.5 |
| 6 | 才轮到调参：α 步长、Beta 先验、聚类阈值、每源配额 | 前 5 步没做时，调参无法归因 | — |

**第 4 步的具体形态（这是唯一一条 D 列为「开跑前必补」却完全没动的）**：`src/refinery/scorer.ts:26-32` 当前是纯命中计数 + sqrt 压缩。归一化的三个候选口径，按侵入性排序：

- **案 a（最小改动）**：`kwPart` 的分母从固定 `√8` 改为 `√min(8, 文本长度档位)`，即长文本要求命中更多关键词才拿满分
- **案 b（矩阵 D5 的方向）**：命中数除以 `log(1 + 文本长度)`，平滑抑制长度优势
- **案 c（换口径）**：只算**标题**命中，正文命中降权（arXiv 的优势全在长摘要）

**三案都会改变通过率，因此必须与 `scoreThreshold=0.45` 一起重新标定**——这正是 §五 第 9 条（公式改两次、阈值一次没动）要避免的重演。**本报告建议：任何打分公式改动，工单验收必须附「新公式下 0.45 阈值对应的关键词/信号词命中组合」以及「实测通过率」两项**（§七 验收纪律）。

**在既有裁决框架内的合法杠杆**：criteria §3b 已定「探针期不改排版」（防位置偏倚干扰），四方矩阵 ⚪ 已定「探针期不做中文分词 / 向量库 / 微调」。所以 Q3 在探针期内的合法动作**只有第 1–3 步（修仪器）与第 4 步（去偏倚）**，第 5、6 步属加注后任务（`workplan` Phase E 已把「条目特征权重 A7/D2 与中文分词 C1」列为加注后首批）。

**最该补的一个埋点**：fati-server 报告 D 提议「回源点击率」（用户是否真的点了证据链接）。**domain-bot 有对应物且更简单**：digest 里每条都带 `[来源](url)`（`file.ts:17`、`telegram.ts:21`），但**没有任何机制记录用户是否点了它**。Telegram 侧可用 inline 按钮 `🔗 打开原文` 走同一套 callback 机制（与 `👀 已读` 同构，`receiver.ts:34-40` 已有先例）。**这条能直接测「信息本身是否被消费」，而不只是「digest 是否被打开」**——比 G-1 的 viewed 更接近需求本体。列为 §七 B′4（可选，签字前决定要不要进判定线；**若进，就是改判据，必须签字前定**）。

### Q4｜如何自进化，让每个 bot 成为领域专家

**domain-bot 的自进化只有一条回路：源权重学习。**（对照 fati-server 侧的「三者合一」——知识包定懂不懂、战绩定准不准、反馈定值不值得推——domain-bot 只有第三项，且是**源级**而非 bot 级。）

**它在两周内能做到什么，已经有精确答案，而且答案是否定的**：

| 层次 | 结论 | 出处 |
|---|---|---|
| **统计功效** | 每天推 6 条 × 14 天 ≈ 84 条，7 源分下来**每源约 12 次反馈**；Beta(1,1) + α=0.2 下 12 条最多推动权重 **±0.15** → **无法区分「真偏好」与「随机波动」** | D `review-2026-09-02-external.md:303-305`，四方汇总 `:50` 采纳 |
| **先验保持** | 每次反馈变更触发全体回归一步，12 次后 `0.8¹² = 6.9%` → **人工先验几乎抹除，权重系统约等于全 0.5** | **本报告 §3.1（新增）** |
| **归因粒度** | 反馈只归簇代表条目的源，簇内其他源零信号；且代表位由加权分决定 → **富者愈富闭环** | **本报告 §3.3（新增）** |
| **实际触发** | 651 条归档 `hitCount` 全为 1、`isNewRate` 轮3=1 → **去重 / 聚类 / 旧闻降权在真实数据上从未触发过一次** | 本报告实测（§1.1） |

**四层叠加的结论**：

> **探针期内「自进化」只能验证一件事——回路通不通（反馈能进来、权重会动、观测能读出）。它验证不了「学得准不准」，而且在当前设计下，它连「人工先验被保住」都做不到。**

这与 criteria 自己的定位一致（§3 标题即「通过线（注意：**通过 ≠ 证实**）」，`:43`、四方汇总 `:50`「探针期只验证『回路通』，不验证『学得准』」），**本报告只是把「回路通」这个目标的下限也标出来了：当前连「通」都还没验过（零反馈、零已读、`feedback.json` 与 `views.json` 均不存在）。**

**关于「成为领域专家」**：domain-bot 当前**没有 bot 实体**——它是单个进程、单个领域（`config/domain.json` 的 `domain: "ai-llm"`）、单套关键词。fati-server 报告里的「bot 实体化（botId ↔ personaId ↔ territoryId 三套 ID 收敛）」在这里的对应物是：

```
一个 bot = 一份 config/（domain.json + sources.json + push.json）+ 一个 memoryDir
```

**这个映射在代码里已经成立**：`src/index.ts:196-217` `main()` 从 `process.cwd()` 读 config，`startBot(opts)` 接受 `memoryDir` 参数（`:222`），`acquireLock(memoryDir)`（`:240`）按 memoryDir 做单实例隔离。**所以「多 bot」在 domain-bot 里等于「多份 config + 多个 memoryDir + 多个进程」，零架构改动即可复制**——这是它作为资产层最值钱的一点，也是 fati-server 报告 §1.2 认定它「三者中最成熟」的实质理由。

**但复制的前提是 §4.2 的 SSRF 与 §4.6 的配置装饰项先修**：单 bot 时 `sources.json` 由老张手工维护，多 bot 时若开放自助添加源，`rss.ts:38` 零校验就从「攻击面低」变成「攻击面敞开」。**这是「收编前必修」而非「探针期必修」的判据来源。**
