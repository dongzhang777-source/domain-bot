# 对 DeepSeek《自进化领域专家 Bot》方案的评审（ZCode / 小智，2026-09-01）

> 评审对象：`.hermes/plans/2026-09-01_150921-domain-expert-bot.md`
> 结论：**架构方向对，可以保留三环模型；但方案 80% 的篇幅在讲管道（plumbing），而决定成败的两个难点恰好被带过了。不建议按原 Task 1-12 直接开工。**

## 一、判断对的地方

1. **"自进化 = 记忆库 + 反馈回路，不重训模型"** —— 这是全方案最值钱的一句话，方向完全正确。
2. 三环模型（采集广 → 提炼深 → 进化闭环）分层清晰，验收标准可证伪，风险节里主动承认了"自我固化"问题。这些都不用改。

## 二、被带过的两个真正难点

### 难点 1：价值打分是整个产品的全部，方案只有一句话
"本地模型对每条信息问 3 个问题"是全文最关键也最空洞的一行。冷启动时，小模型/关键词根本判断不了什么叫"反常识、高杠杆"——方案自己在风险节承认了，但没有给出解法。验收标准 #2（100 条噪音选出真有价值的）其实就是全部难度所在，其余 11 个 Task 都是为它服务的管道。

### 难点 2：反馈回路存在鸡生蛋矛盾，MVP 自相矛盾
- 环3（进化）依赖 viewed/clicked/dismissed 反馈信号；
- 但推送渠道被推到"实现时再定"，MVP 默认本地文件——**本地文件没有反馈回路，验收标准 #3（进化）在 MVP 里根本跑不起来**。
- 推送渠道不是细节，它是反馈回路的传感器，必须在设计期定下来。

## 三、技术层面的具体问题

1. **个人反馈样本量撑不起 bandit**。每周几十次点击的信号量，直接做源权重升降会剧烈抖动。fati-server 的 bandit 之所以成立，是因为它跑在内容生产规模上；这里需要加 ε-探索和长时间窗平滑，方案没提。
2. **去重测试标准写反了**。Task 2 要求"轻微改写判定为不同"——但新闻场景真正需要的是把"同一事件多源报道"聚成一条（近似重复检测，靠 embedding 相似度），哈希去重只是平凡部分。方案把容易的当成了测试重点，难的略过了。
3. **采集适配器是真实的维护成本黑洞**。列了 8 个平台（X/微博/Reddit/B站…），每个都有反爬、API 收费、封号问题。MVP 应只做 RSS + arXiv + GitHub 三个免维护源。
4. **向量记忆库没必要从零写**。tuna 已有 embedding 架构实践（见技能 tuna-embedding-architecture），至少应该先读它的取舍再决定自研。

## 四、与工作区的联系（比方案里写的更深）

方案 §二 只写了"提炼环可复用 fati-server 思路"，但真正的联系是：

1. **这个 bot 本质上是 fati-server"千 bot 工厂"路线的消费端实例**。fati-server a114036 终审裁决的核心待验证命题是"需求 50"——用户到底要不要千 bot。一个"帮我盯某个领域、越用越懂我"的个人专家 bot，正是该需求最具体的形态之一。**建议把它定位成阶段 0 假门测试的一个真实探针，而不是第 6 个独立子项目。**
2. 提炼环的"是否已知/是否有增量"判定 = claim graph 的去重与增量问题，两边是同一个算法问题，先在 bot 侧做小规模验证，结论可反哺 fati-server。
3. 推送渠道建议直接用 **Telegram**：工作区已有完整的 hermes-telegram 网关经验（技能 hermes-telegram-setup / multi-machine-telegram），且 Telegram 是天然带点击反馈的交互渠道，一举解决难点 2。

## 五、修改后的 MVP 建议

一个领域、三个免维护源（RSS/arXiv/GitHub）、Telegram 推送、摘要尾部带 👍/👎 反馈、ε-greedy 源权重。跑两周看三件事：推送精确率（人工抽查）、反馈率、源权重是否稳定收敛。**先验证价值打分冷启动能不能成立，再谈自进化。**
