## 一、七条定向问题

### 问题 1：探针逻辑本身——一个 bot + 一个用户 + 两周，能为"千 bot 需求"提供有效证据吗？

**结论：有条件反对。** 它能为"作者本人会不会用这个 bot"提供证据，**不能**为"用户要不要一万个 bot"提供证据。

**理由：**

brief 自己说这个探针是为了验证"需求 50"。但从 n=1（且 n=1 是设计者本人）到"一万个 bot 有需求"，
中间的推断跳跃不是"样本量不够大"这种可以靠加样本修补的问题，而是**测错了变量**：

- "千 bot 需求"的真实不确定性不在"bot 有没有用"，而在"**非作者用户**愿不愿意配置它、容忍它的噪音、为它付费"。
- 这三个变量在"作者自测两周"里**一个都没有被触碰**。作者不需要配置（他自己写的）、
  对噪音的容忍度是设计者特权（他知道为什么推这条）、付费意愿无从测起。

**通过线的具体问题（这部分是可修的，比逻辑跳跃严重性低）：**

| 通过线 | 问题 |
|---|---|
| 👍 率 ≥ 30% | **这是个无效指标**。二元 👍/👎 按钮有强烈的"默认不点"偏差。若作者只点 👍 从不点 👎，👍率 = 100%，探针大获成功，信息量为零。真正该测的是**反馈率**（有反馈的推送 / 总推送），👍率只在反馈率达标时才有意义。**必须给 #2 补一个反馈率下限**（建议 ≥20%）。 |
| 主动查看 ≥ 10 次 | **定得太松，松到通过与否无法区分**。`DOMAIN_BOT_POLL_MS` 默认每小时一轮，两周 = 336 轮。10 次查看意味着 **97% 的推送从未被看**。这个通过线会让"其实没人看"和"有需求"同时判为通过。建议改为与轮数成比例（如 ≥30% 的推送被查看）。 |
| 第 3 轮起噪音可感知下降 | **这条会产生假阳性**，见问题 3 的混淆变量分析。这是四条里最危险的一条。 |
| 加一个领域 = 改一份 config | **从未实测过**。brief 的"证据"栏写的是设计意图，不是观测结果。见问题 6。 |

**可证伪的反对意见（对我自己结论的攻击）：**

如果作者的目的是 dogfooding（"验证我自己会不会用"），那 n=1 是**恰当**的设计，我的批评不成立。
但这个目的与 brief 声称的"为需求 50 提供证据"是两件事。
**最小修复方案：把探针的结论边界明确改写为"作者本人留存信号，不外推到千 bot 需求"。**
如果作者不接受这个降格，那就必须现在就加 3 个非作者用户，否则两周后的结论在逻辑上撑不住投入决策。

反过来说，我这个批评也可以被一个观测证伪：**如果两周内作者自己的查看率低于 30%，
那连 dogfooding 都没通过，"千 bot"讨论直接终结**——这也是为什么我主张把 #1 的通过线改成比例制。

### 问题 2：自进化技术路线的天花板，以及 Beta(1,1) + α=0.2 是否稳健

**结论：同意路线，反对当前参数与当前接线状态。**

**理由：**

**(a) 路线方向正确，但天花板很低，且天花板的位置与 brief 设想的不同。**

"不重训模型 + 记忆库 + 反馈回路"是唯一现实的选择，这点没问题。
但天花板不在"信号量小"（brief 担心的），而在**学习信号的维度**：

- 源权重是极粗粒度的信号。一个源内部同时含高价值和噪音（arXiv 既有 SOTA 也有灌水），
  按源调权只能整体放大/衰减，**无法学到"这个源里的哪类内容好"**。
- 学习信号的维度 = 源数量（当前 7），内容空间的维度是无限的。
- 这条路线能收敛到的上限是"哪个源平均更好"，**不是"什么内容更好"**。

所以两周后即使源权重完美收敛，学到的东西也只是"arXiv 比 V2EX 好"——这是不需要两周就知道的先验。

**(b) α=0.2 在预期信号量下不稳健，原因是双重平滑里 EMA 的 α 固定。**

`sourceValue` 用 Beta(1,1) 后验均值，这层平滑是对的。但 `updateWeights` 又叠了一层固定 α=0.2 的 EMA。算一下量级：

- 每周几十次反馈分散到 7 个源 → 每源每周约 3-5 次反馈。
- Beta(1+up, 1+down) 在 n=5 时，后验均值的标准差约 **0.2**。
- α=0.2 的 EMA 对观测噪声的抑制有限，权重会随机游走在 **±0.1** 量级。
- 而 `applySourceWeight` 的乘数是 `(0.5 + w)`，w 的实际取值范围 0.2~0.6 → 乘数范围 **0.7~1.1**。

**权重噪声量级（±0.1）与权重有效范围（0.4）同阶。** 学习信号会被噪声淹没。
这不是"抖动"（brief 的说法），是**信噪比不足**——抖动可以靠平滑解决，信噪比不足只能靠增加信号或降低维度解决。

**(c) 最严重的：这两个函数在生产路径上从未被调用。**

`grep -rn "updateWeights" src tests` 结果：`src/memory/evolve.ts` 里只有定义，
唯一调用点在 `tests/evolve.test.ts` 和 `tests/e2e.test.ts`。
`updateWeights` 的返回值也**没有任何写回 `config/sources.json` 的路径**，而 `main()`（`src/index.ts` L156-157）
每轮重新 `loadJson` config。

即使把反馈回路接通，权重也只在内存里活一轮，下一轮从 config 初值重来。
实测印证：`memory/` 下**只有 `archive.json`，没有 `feedback.json`**——5 轮真实运行产生 **0 条反馈**。

**具体建议：**
1. α 应与反馈量挂钩（反馈少时 α 更小），或者**直接用后验均值当权重、不做 EMA**——Beta 平滑本身已经处理了小样本，双重平滑里第二重的固定 α 反而引入了对旧值的过度依赖。
2. 权重必须持久化。建议写 `memory/weights.json`（而非污染 `config/sources.json`），`main()` 启动时读它覆盖 config 初值。
3. **先实测反馈量再定 α，不要先定 α。**

**可证伪的反对意见：**

如果实际反馈量远大于预期（作者每天点 20 次），α=0.2 是合理的，我 (b) 的批评失效。
这个批评可以被一个半小时的实验直接证伪：**跑 100 轮模拟，每轮注入 3 次随机反馈，
画出权重轨迹，看方差是否 << 0.2。** 如果方差远小于 0.2，我错了。
建议把这个模拟做成 `tests/` 里的一个用例——它同时能验证 (c) 修好之后的端到端行为。

### 问题 3：价值打分冷启动——过渡方案还有什么更大的坑

**结论：brief 对自己问题的描述偏轻了。真正的坑不是"偏袒 arXiv"，是三个更硬的缺陷。**

**理由：**

**(a) 打分饱和 → 完全丧失区分度（实测证实）。**

`valueScore = Math.min(1, 0.3 + 0.15 * kwHits + 0.12 * signalHits)`，而 `config/domain.json` 有 **17 个关键词**。
arXiv 摘要长，命中 5 个关键词极易：`0.3 + 0.15*5 + 0.12*1 = 1.17 → min → 1.00`。

实测 5 份 digest 的分数分布（交叉审查阶段补齐的完整数据）：
**轮 1/3/4 的 arXiv 推送连续 18 条全部触顶 1.00**，轮 5 的 arXiv 3 条也是 1.00；
唯一有区分度的是 exa（轮 2：`[0.76, 0.76, 0.63, 0.63, 0.49]`）。
触顶即丧失区分度——**arXiv 侧的排序退化为 RSS 原始顺序**。
这不是"偏袒 arXiv"，是"对 arXiv 完全不打分"。

**并且这个饱和会掩盖质量衰减**：传送带在消耗候选池（见问题 5 #2），真实质量在降，
但分数恒为 1.00，**打分器对衰减零灵敏度**。

顺带一个反向印证：exa 是唯一有区分度的源，因为它的 highlights 短（截断 1200 字符但实际更短），
关键词命中天然少。而 **exa 是语义搜索（上游已筛选过），arXiv RSS 是全量未筛选**——
打分器在惩罚上游已经做好的筛选工作，奖励未筛选的长文本。

修法：`kwHits` 改为归一化（`kwHits / keywords.length`）或对数压缩，起步分从 0.3 降到 0。

**(b) `scoreThreshold` 是装饰品——0 条会被它过滤掉（可算术证明）。**

- `filterRelevant`（`src/refinery/filter.ts`）要求**至少 1 个关键词命中**才通过。
- `HeuristicScorer` 用**完全相同**的匹配逻辑计 `kwHits` → 通过相关性的条目必然 `kwHits ≥ 1`。
- 所以 `valueScore ≥ 0.3 + 0.15 = 0.45`。
- `applySourceWeight` 乘 `(0.5 + w)`，w 最低 0.2 → 有效分 **≥ 0.45 × 0.7 = 0.315**。
- 而过滤线是 `scoreThreshold * 0.5 = 0.45 * 0.5 = **0.225**`。

**0.315 > 0.225 → 通过相关性过滤的条目 100% 通过打分阈值。**
brief 说"过滤后约 960 条相关"——那 710 条全是相关性过滤杀的，打分阈值一条没杀。
"价值打分"在冷启动阶段的实际作用**只是排序**，而 (a) 又说明排序在 arXiv 上饱和了。
唯一真正起作用的选择压力是 sort + 每源配额。

**(c) 两个死信号词。**

`signals` 里的 `'state-of-the-art'` 和 `'open-source'` 含连字符，
但 `hay = normalizeText(...)` 已经把 `[^\p{L}\p{N}]+` 全替换成空格（`src/collector/dedupe.ts` L8）——
**归一化后的文本里不可能存在连字符**。这两个信号词永不命中，11 个实际只有 9 个有效。
（`'open source'` 带空格的那个能命中，所以功能上有部分重叠，但这是巧合不是设计。）

**(d) 切到 LLM 打分那一刻会直接崩，且不降级——这是"LLM 接入前"之后最大的坑。**

`LlmScorer.score`（`src/refinery/scorer.ts` L47-83）：

1. **没有分批**。它把全部 `relevant` 条目（brief 实测约 960 条）塞进单个 prompt，每条 body 截断 600 字符
   → 约 60-70 万字符，远超任何模型上下文窗口。
2. **没有兜底**。`JSON.parse(match[0])`（L71）无 try/catch；
   而 `runOnce` 对 `scorer.score()` 也**没有 try/catch**（`src/index.ts` L64）。
   → LLM 输出格式不合预期时**整个管线崩溃，不会降级到启发式**。
3. brief 说"无 LLM key 时启发式打分兜底"——准确，但**有 key 而 LLM 输出坏掉时无兜底**。
4. 解析失败时默认 0.5 分（L73）：所有条目同分 → 排序完全退化，
   且 `0.5 × (0.5+w)` 恒 > 0.225 → **全部通过阈值，静默产出看似正常实则随机的 digest，无任何告警**。

**每源配额本身是有效的**（实测 18:35 那轮 `{arxiv:3, hf:2, github:1}`），但它治的是症状。

**可证伪的反对意见：**

(a)(b) 是算术与实测，我认为不可反驳。可反驳的是它们的**严重性判断**：
如果作者认为"冷启动阶段打分只需要粗排序，不需要精确区分"，那么饱和与阈值失效都是可接受的，
我的 (a)(b) 就降级为"技术债"而非"坑"。
但 (d) 不可降级——它会让探针在填上 LLM key 的那一刻挂掉，而填 key 正是 brief 计划中的下一步。

### 问题 4：渠道策略——排除登录态通道的伤害有多大，有没有两全方案

**结论：同意取舍，但 brief 高估了当前渠道的实际产出。真实伤害不在"缺 Twitter/Reddit"。**

**理由：**

排除登录态通道的决定是对的（封号风险 + 无人值守不兼容，这个判断我完全支持）。
但实测数据显示：**已接入的免登录通道也有一半是死的。**

5 轮真实运行的归档 29 条，按源分布：

```
arxiv-cs-ai          21
exa-llm-news          5
huggingface-blog      2
github-new-llm-tools  1
v2ex-hot              0   ← 零产出
bili-llm              0   ← 零产出
hf-daily-papers       0   ← 零产出（jina，缺 key → 401）
```

所谓"7 源"实测只有 **4 源在产出**，其中 1 源（arXiv）占 72%。

**根因是结构性的，不是配置疏忽：**

1. `config/domain.json` 的 17 个关键词**全是英文**，而 v2ex / bili 返回**中文内容**
   → `filterRelevant` 的 `hay.includes(k)` 结构性 0 命中。这两个源不是"效果差"，是**不可能有效果**。
2. `fetchV2ex`（`src/collector/adapters/agentreach.ts` L72）**硬编码了 URL**，完全忽略 `source.url`
   → config 里该字段是装饰，"改 config"改不动它。
3. `fetchBili` 用正则解析 YAML（L93）：
   `/- id: (\S+)[\s\S]*?bvid: (BV\S+)[\s\S]*?title: (.+)[\s\S]*?author: (.+)[\s\S]*?play: (\d+)/g`
   字段顺序或缩进一变即**静默返回 0 条**（不抛错）。
4. **当前没有任何"源产出为 0"的告警或每轮统计。** `runOnce` 的 `stats` 只记 `collected/deduped/relevant/pushed`
   和 `skippedSources`（后者恒为空，因为 ε-greedy 删除后 `skipped` 数组从未被 push 过）。
   → **静默死亡无法被发现**。这三源可能已经死了 5 轮而作者不知道。

**两全方案（按可行性排序）：**

1. **Reddit 的 `/.json` 端点无需登录**，风险远低于账号爬取；rsshub 类桥也能覆盖 Twitter/小红书的一部分。
   这是"两全"最具体的路径——不是"要不要登录态"的二元选择，而是"有没有免登录的替代端点"。
2. **保持排除，但加人工触发入口**：`npm run fetch:x -- --query ...`，作者想看时手动跑一次。
   封号风险由"人在环"控制，信息质量缺口按需补。这与无人值守管线不冲突。
3. 对中文源配中文关键词——但这会撞上问题 6 的分词缺陷，**必须先修分词**。

**可证伪的反对意见：**

如果 exa 语义搜索质量足够高（它 weight 0.6，是配置里最高的），那么缺 Twitter/Reddit 的伤害可能很小——
exa 本身索引了大量社交内容，这个批评就大幅减弱。
但实测 exa **5 轮只产出 5 条，且集中在单独一轮**（18:31:09），其余 4 轮为 0。
说明 exa 通道自身也不稳定（`mcporter` CLI 依赖 + 90s timeout）。
**若 exa 能稳定产出 20+ 条/轮，我的结论要改。** 这也是个可查的观测点。

### 问题 5：防自我固化——还有什么机制层面的固化风险

**结论：反对。brief 列的三项机制里，两项在当前代码中不生效；而真正的固化风险一项都没提到。**

**理由：**

**先核 brief 列的三项：**

| 机制 | 实际状态 |
|---|---|
| 记忆库可人工修正 | **部分成立**。纯 JSON 确实可改，`tests/store.test.ts` L36-49 也测了。但 `memory/` 在 `.gitignore` 里 → 人工修正无版本记录，改错无法回滚。且 archive.json 现 29 条 / 14.6KB，两周后约 2000 条 ≈ 1MB，**人工审查不现实**。 |
| 源权重向 0.5 先验回归 | **运行时不存在**。`sourceValue({up:0,down:0}) = 1/2 = 0.5` 的数学是对的，但 `updateWeights` 从未被调用（问题 2c）。 |
| ε-greedy 已删除改全量抓取 | **决定正确**，但它同时移除了唯一的探索机制。全量抓取解决"不漏源"，不解决"不漏源内的好内容"。 |

**brief 没提到的固化风险（按严重性排序）：**

**#1 关键词硬门是整个系统最强的固化机制，而自进化回路碰不到它。**

`isRelevant` 是 `domain.keywords.some(k => hay.includes(k))` —— **0/1 硬门**。
不在关键词表里的内容永远进不了管线，也就永远不可能通过反馈被学到。

对比一下：源权重是**软**的（乘数 0.5~1.5，最坏情况把某源压到 0.7 倍），
关键词是**硬**的（直接丢弃）。brief 实测 1670 → 960，**710 条（43%）在硬门处被丢掉，且永久不可召回**。

**整个自进化回路没有任何路径可以修改关键词表。**
所以"防自我固化"的三项机制全都在软层做文章，硬层完全敞开。

建议：让反馈能**提议新关键词**——从 👍 条目的标题提取高频 token，人工确认后加入 `keywords`。
这是把硬门变成可学习的唯一途径，且实现成本极低。

**#2 归档传送带：系统只会单调下滑，且无法回头重评。**

`store.recordItems(scored, now)`（`src/index.ts` L95）里 `scored` 已被截断为 diversified（≤6 条），
所以**归档只存被推送的条目**（README「已知边界」已披露这点，如实记账）。
后果是 `knownIds()` 的对照库极小，而 `dedupe` 是无条件的：

- 第 1 轮：arXiv 返回当天 ~100 条，推打分 top 3，归档这 3 条。
- 第 2 轮：同一批 RSS，那 3 条被 dedupe 挡掉 → 推第 4-6 名。
- 第 N 轮：推第 3N 名之后。

**实测印证：18:31:28 与 18:31:41 两轮间隔 13 秒，各推 6 条完全不同的 arXiv。**
13 秒内内容源不可能更新，所以第二轮推的必然是第一轮之后的名次——传送带效应已被实证。
另：归档 29 条中 `hitCount > 1` 的是 **0 条**，说明没有任何条目被重复见到，与传送带模型一致。

README 说"打分器变好后可捞回"——**但代码里没有任何捞回机制**，dedupe 无条件屏蔽。

**这一条直接摧毁假门标准 #3，见下面的混淆变量分析。**

**#3 打分器固化。** `signals` 是硬编码的 11 个英文词（其中 2 个还是死的，见问题 3c），反馈回路无法修改它。

### 问题 6：可复制性声明——当前实现离"改一份 config"还差什么

**结论：反对。差的东西里有一项是致命的，且我用可执行探针实测确认了。**

**理由：**

**致命项：`tokenize` 不做中文分词，导致聚类与新颖性判定在中文上完全退化。**

`tokenize`（`src/collector/dedupe.ts` L12-14）按空格切分：

```typescript
export function tokenize(s: string): Set<string> {
  return new Set(normalizeText(s).split(' ').filter((t) => t.length > 1))
}
```

中文字符属于 `\p{L}`，`normalizeText` 会保留它们，只把标点换成空格。
所以中文标题被切成"标点分隔的长块"，不是词。我写了探针脚本直接调 `dist/` 里的真实函数，实测输出：

```
--- 中文 tokenize ---
"大模型推理优化最新进展：vLLM 发布新版本"   → [ '大模型推理优化最新进展', 'vllm', '发布新版本' ]
"大模型推理优化最新进展：vLLM 发布了新版本" → [ '大模型推理优化最新进展', 'vllm', '发布了新版本' ]
"大模型推理加速的最新研究成果分享"          → [ '大模型推理加速的最新研究成果分享' ]   ← 整句 1 个 token

--- jaccard（聚类与新颖性判定的核心度量）---
中文 A vs B（近似重复，应判重）  : 0.500
中文 A vs C（同主题，应可聚类）  : 0.000   ← 完全不聚类
英文 A vs B（近似重复，应判重）  : 0.667
```

推论（全部可由上面的实测直接推出）：

1. **无标点、无中英混排的纯中文标题 → 整句 1 个 token → 任意两条不同标题 jaccard 恒为 0。**
2. `buildClusters` 阈值 0.35 → 中文同主题多源报道**永不聚成一簇**，"同事件合一"在中文上失效。
3. `isNovel` 阈值 0.7 → 中文标题除非完全一致，**恒判为"新"**，"旧闻降权"在中文上彻底失效。
4. 关键词过滤**可用**（实测 `isRelevant(中文标题, 关键词"大模型") = true`），因为 `includes` 是子串匹配。

所以中文领域下的实际能力是：**能采集、能过滤，但不能聚类、不能判新颖。**

**这一条对"千 bot 工厂"尤其致命**：fati 与 fati-tavern 都是中文产品。
若千 bot 面向中文内容市场，当前核心算法在中文上失效，"改一份 config 即可复制"**不成立**。
而问题 4 已经实测到 v2ex / bili 两个中文源零产出——这不是巧合，是同一个根因的两个表现。

**顺带发现一个阈值语义自相矛盾（英文中文都中招）：**

`clusterThreshold = 0.35`，`isNovel` 阈值 = `0.7`。两者之间存在盲区带：
标题 jaccard ∈ [0.35, 0.7) 的两条内容，**既被 `clusterItems` 判为"同一事件的多源报道"聚成一簇，
又被 `isNovel` 判为"新信息"打上 🆕增量标记**。同一份内容，系统同时说"这是旧事件的另一篇报道"和"这是增量新信息"。

实测印证：`outbox/digest-mtj8wzm8.md` 里 **6/6 条全部标 🆕增量** → 该标记零信息量。
补充：`isNew` 只在 `src/push/file.ts` L17 用作展示标签，
**不参与 `valueScore`、不参与排序、不参与过滤**（`src/index.ts` L66-73 只用 `valueScore`），
而 Telegram 渲染（`renderDigestText`）连这个标签都不显示。
所以假门标准 #3 里的"旧闻降权"在两个推送通道上都**零实现**。

**其余阻碍"改 config 即可复制"的具体项：**

| # | 问题 | 位置 |
|---|---|---|
| 1 | 中文分词（见上，致命） | `dedupe.ts` L12 |
| 2 | 关键词语种必须与源语种匹配，config 无任何校验 | `domain.json` / `sources.json` |
| 3 | `fetchV2ex` 硬编码 URL，忽略 `source.url` | `agentreach.ts` L72 |
| 4 | `fetchExa` / `fetchBili` 依赖本机装了 `mcporter` / `bili` CLI 且已登录 → 换机器静默失败 | `agentreach.ts` L53, L91 |
| 5 | 源产出 0 时无告警无统计 → 接入者无法发现配错 | `index.ts` L119-128 |
| 6 | `LlmScorer` 的 prompt 硬编码中文（`领域：${domain.domain}`）→ 换英文领域要改代码 | `scorer.ts` L50 |
| 7 | `push.json` 的 `channel` 字段被读入但从未使用（L158 读了，L108 只判断 `opts.outDir`）→ 装饰性配置项 | `index.ts` |

**最小可验证方案（半天工作量，且产出直接就是标准 #4 的证据）：**

真的去加一个非 AI 领域（比如"精酿啤酒"或"Massachusetts 地产"），**全程只改 config，
记录每一处被迫改代码的地方**。当前 brief 的标准 #4"证据"栏写的是设计意图，不是观测结果。
这个实验做完，#4 才有资格被判"通过"或"不通过"。

**可证伪的反对意见：**

如果"千 bot"明确只面向英文领域，那中文分词缺陷不构成本探针的阻塞项，
我的"致命"定级应降为"路线限制"。
但那样一来 v2ex / bili 两源就该直接从 config 删掉（它们结构性零产出），
且结论文档必须写明"本探针只验证英文领域"——**否则 #4 的通过是虚假的**。

### 问题 7：两周后的决策框架

**结论：brief 只给了通过线，没给失败线的处置，也没区分"信号无效"和"信号为负"。这是最需要补的一块。**

**理由：**

当前设计**无法区分**这两种情况，因为 #1 无埋点、#2 无生产代码路径。
"没观测到反馈"既可能是"用户觉得没价值"，也可能是"反馈根本没被记录"。
这两者的处置完全相反（前者该放弃，后者该修代码重跑），
而现在它们会产出同一个观测结果。

**判据设计（前提是先修好第 2 节 A/B/C 三项的可测性）：**

核心改动：**以反馈率为第一序判据，👍率为第二序。** 反馈率测的是"用户愿不愿意交互"（这是产品前提），
👍率测的是"内容好不好"（这是质量问题）。前提不成立时讨论质量没有意义。

| 观测组合 | 判读 | 处置 |
|---|---|---|
| 查看率 < 30%（比例制，见问题 1） | 作者自己都不用 | **放弃**。最强负信号，且无法用"设计问题"辩解——设计者本人是容忍度最高的用户 |
| 反馈率 < 10% | 用户懒得反馈 → "显式反馈回路"这个设计前提不成立 | **放弃"自进化"卖点**，改做纯推送产品；或把反馈改成隐式信号（点击/停留/转发） |
| 反馈率 ≥ 20% 且 👍率 ≥ 60% | 内容有价值且用户愿意反馈 | 加大投入，但**必须先做 n>1 验证**（3 个非作者用户跑两周），否则回到问题 1 的逻辑缺口 |
| 反馈率 ≥ 20% 且 👍率 30~60% | 通道对，打分不准 | **改设计重跑**：接 LLM 打分（先修问题 3d 的崩溃路径），重跑两周 |
| 反馈率 ≥ 20% 且 👍率 < 30% | 用户在看但觉得是噪音 | **改设计重跑**：问题在采集源或关键词硬门（问题 5 #1），不在打分 |
| 源权重轨迹方差 > 均值变化量 | 学习信号被噪声淹没（问题 2b） | **改设计**：反馈量不足，换隐式信号或扩大用户数；调 α 无意义 |
| 候选池 top-N 快照质量未升，但实际推送噪音下降 | 传送带效应，非自进化（问题 5 #2） | **判定标准 #3 无效**，不得计入通过 |

**最后一行是专门给混淆变量设的防线**——它要求同时记录"候选池快照"和"实际推送"，
才能把两者分离。这是我建议必须在跑之前加上的观测点。

**方法论上最重要的一条：**

两周后该问的不是"通过线过了吗"，而是
**"我获得的证据能否区分'需求存在'和'需求不存在'？"**

如果答案是"不能"（当前实现就是这样：#1 无埋点、#2 无回路、#3 有混淆变量、#4 未实测），
那这两周的产出是**零**，不该据此做任何投入决策——无论观测到的数字多好看。

## 二、无限定问题区

### 1. 这个探针最大的风险不是失败，是假成功

把三条串起来看：

- 标准 #1 只能靠作者自觉手记（**自我报告数据**，而 brief 偏见声明 #1 自认作者是利益相关方）；
- 标准 #2 在拿到 Telegram token 前，唯一反馈通道是 digest 里那句"或向 `feedback.json` 追加记录"——
  **手工编辑 JSON 文件**。用手改 JSON 的摩擦测出来的 👍率，测的是作者勤快程度，不是内容价值；
- 标准 #3 存在传送带混淆变量，会在自进化完全未工作时判为通过。

**最可能的两周后场景**：作者看到"噪音确实在下降"（传送带）、"我确实点了不少 👍"（自己手记的）、
"查看次数超过 10 次了"（336 轮里的 10 次），四条标准全过
→ 千 bot 路线获得投入理由。而这四条**全部可能是测量假象**。

**一个设计成会假阳性的假门，比没有假门更危险**，因为它会终结讨论。
brief 的偏见声明写了四条防事后合理化，考虑得比大多数方案周全，
但它防的是"作者主观高估"，没防"测量机制客观失真"——后者不需要作者有任何主观动机就会发生。

### 2. 「测试 35/35 绿」被 brief 当成正面证据列出，但它与假门可测性无关

我跑了测试，确实 35 绿（`Test Files 8 passed (8) / Tests 35 passed (35)`）。这个数字是真的。
但它证明的东西比 brief 的措辞暗示的少得多。

关键在 `tests/e2e.test.ts` L70-85 那个名为「反馈回路：👍 后源权重上升，进化可复算」的用例：

```typescript
const r = await runOnce({ ... })              // 只有这一步是产品代码
const store = new MemoryStore(join(dir, 'memory'))
const ref = r.digest!.clusters[0]!.ref
const resolved = store.resolveRef(ref)!        // ↓ 以下三行是测试代码手工串的
store.recordFeedback({ ... })
const next = updateWeights(sources, store.feedbackBySource())
expect(next[sourceOfCluster]!).toBeGreaterThan(...)
```

`runOnce` 之后，**测试自己**调了 `resolveRef → recordFeedback → updateWeights`。
它证明的是"这三个零件各自可用"，**不是"产品会把它们装上"**。
生产入口 `src/index.ts` 从头到尾没调用过其中任何一个。
而且它连"权重被写回、下一轮生效"都没断言——那正是缺失的那一环。

**这与工作区 AGENTS.md 记录的 codex「自制沙箱假通过」教训是同构复现**：
> 验收必须读自测代码本身，不能只看 ALL_PASS。

我读了自测代码本身，才发现绿的是零件不是机器。

建议：**e2e 用例必须从一个真实的 callback 入口驱动**（哪怕是个最小的 `getUpdates` 处理函数），
否则它测的是虚构的装配。修好问题 2c 之后，这个用例应该改成"调入口 → 断言 `weights.json` 变了"。

### 3. 与工作区的真实联系被 brief 低估了

brief 只说 domain-bot 是 fati-server 千 bot 路线的探针。但更具体的复用关系没写：

**tuna 已经有同构的三件套**（见 tuna 知识库「TUNA 内容流水线」）：

| domain-bot 自己写的 | tuna 已有的 |
|---|---|
| `collector/adapters/rss.ts` RSS 抓取 | `packages/feeds` 网络内容源抓取与清洗管道（RSS + BYO 搜索） |
| `types.ts` RawItem 归一化 | `packages/content` ContentNormalizer + JSON Schema 校验 |
| `scorer.ts` 的 `reason` 字段当"为什么值得看" | `packages/brief`「为什么推给你」生成管线 |

domain-bot 的采集环、归一化环、推荐理由环与 tuna 的 feeds/content/brief 三包高度同构，
**却是独立重写的**——连 `tokenize` 都自己写了一遍，并且写出了问题 6 的中文分词缺陷。
tuna 的编码规范里明确写了"所有外部不可信输入在进入提示词前经 sanitize 清洗并截断码点长度"，
而 domain-bot 的 `LlmScorer` 直接 `it.body.slice(0, 600)` 按 UTF-16 码元切（会切断代理对），没有码点处理。

**对"可复制性"的直接含义**：如果千 bot 工厂真要跑，bot 之间**必须共享这些基础件**，
否则每个 bot 都带一份自己的分词器 bug 和自己的 sanitize 缺陷。

这也直接回答了"无数 bot 能不能跑通"——
**如果每个 bot 都是一份独立代码，不能。** 千 bot 的可复制性不取决于 config 好不好改，
取决于底层管线是不是共享的。

建议：探针跑完后若结论是继续，**第一步不是加 bot，是把 domain-bot 的采集/归一化层与 tuna 的 packages 合并或反向复用**。
这个动作本身就是对"可复制性"最真实的检验——比"再加一个领域"的检验强得多。

另外 `scorer.ts` L50 的 prompt 里那个三问（"对领域决策有用？相对已知是否增量？是否反常识/高杠杆？"）
是全项目最有价值的一句话，也是 `.hermes/plans/2026-09-01_domain-expert-bot-review-zcode.md`
里前一轮评审指出的"最关键也最空洞的一行"。它现在被实现成了一个**没有分批、没有兜底、会崩溃的** LLM 调用。
从"一句话"到"能跑"之间的那段工程，还是没做完。

### 4. 一个方法论建议：把"作者本人当第一个用户"这个污染源转成资产

brief 偏见声明 #2 说单人用户是最弱证据形态。这个自评是对的，但它漏了一个不对称性：

**作者同时是 AI 从业者（目标用户），这意味着作者的负反馈是高信息量的，正反馈是低信息量的。**

- 如果连设计者本人都觉得是噪音 → 普通用户必然更觉得是噪音（**强负信号**）；
- 如果设计者本人觉得有价值 → 可能只是因为他知道自己为什么推这条（**弱正信号**）。

所以应该**非对称设定通过线**：

- 👍率 < 30% 或查看率 < 30% → **可直接放弃**，无需二次验证；
- 👍率 ≥ 30% → **不可外推**，必须补 n>1 验证才能作为投入依据。

当前 brief 把两个方向对称处理（都当成"通过/不通过"的证据），浪费了这个信息不对称。
非对称设定的好处是：**它让探针在失败时能快速止损，在成功时不会误判**——
而两周探针的真实价值恰恰在前者（快速排除一个昂贵的错误路线），不在后者。

### 5. 文档漂移：README 与 brief 互相矛盾

README 的架构图仍写着 **"ε-greedy 源权重"**，
而 brief 附录 A 说 ε-greedy"已被证明有害并删除（改为全量抓取）"。README 未同步。

这在"可复制性 = 改 config"的声明下是实质问题：
新领域接入者读 README 会去找一个不存在的机制。
同类漂移还有 `src/index.ts` L45 的 `skipped` 数组——ε-greedy 删除后它再也没被 push 过，
但 `stats.skippedSources` 仍在返回它（恒为空数组），是个残留的假接口。

建议：删掉 README 里的 ε-greedy，删掉 `skipped` 死变量，或者把 `skippedSources` 改成真正有用的
**"本轮零产出源列表"**（这正好是问题 4 第 4 点需要的告警）。

## 三、总判断

### 结论：**改设计后值得**

**值得跑的部分（不用改）：**

- 探针的**定位**是对的：把"需求 50"从抽象命题变成可观测行为，这个思路比再写一份方案文档有价值得多。
- **采集环实测能拿到真实数据**：1670 → 960 → 6，管线跑通了，单源失败不阻塞的降级设计是扎实的。
- 排除登录态通道的**取舍判断正确**（问题 4）。
- "自进化 = 记忆库 + 反馈回路，不重训模型"的**路线选择正确**（问题 2）。
- 每源配额**实测生效**（18:35 那轮 3+2+1）。
- brief 的**偏见声明**四条写得比多数方案周全，尤其 #4"把已实现视为零成本选项"。

**按现状跑两周会得到的东西：不是证据，是无法归因的观感。**

四条假门标准的实测状态：

| 标准 | 当前可测性 |
|---|---|
| #1 主动查看 ≥ 10 次 | **无观测手段**。file 推送无任何埋点，`memory/`+`outbox/` 均 gitignored，只能靠作者自觉手记 → 自我报告数据 |
| #2 👍率 ≥ 30% | **生产代码路径不存在**。六个反馈相关函数在 `src/` 内无调用者；实测 5 轮 0 条反馈（`feedback.json` 不存在）。且指标本身设计有误（缺反馈率下限） |
| #3 源权重收敛、旧闻降权 | **两项均无实现**。权重无持久化路径、`updateWeights` 未被调用；`isNew` 只做展示不参与打分，Telegram 通道连展示都没有。**且存在会产生假阳性的传送带混淆变量** |
| #4 改 config 即加领域 | **从未实测**。且中文领域下聚类与新颖性判定实测失效（jaccard 恒 0） |

**修复成本：A/B/C 三节都是"接线"级别，不是重写。估算 1-2 天。**
相比两周的探针周期，这个前置投入显然划算——而且不修的话，两周后大概率要重跑，那才是真正的浪费。

### 跑之前必须做的（按优先级，前 5 项是阻塞项）

| 10 | 统一 `clusterThreshold`(0.35) 与 `isNovel`(0.7) 的语义，消除盲区带；让 `isNew` 真正参与打分，或删掉它并同步修改假门标准 #3 的措辞 | 阈值自相矛盾 + "旧闻降权"零实现（问题 6） | 小 |

### 明确建议**不要**在探针期做的

- **不修中文分词**（问题 6）。那是"加领域"的问题，不是"验证需求"的问题，修它会拖长探针周期。
  但**必须在结论文档里写明"本探针只验证英文领域，中文领域的可复制性未验证"**，
  并且从 config 里删掉 v2ex / bili 两个结构性零产出的中文源，否则标准 #4 的通过是虚假的。
- **不做 n>1 用户验证**。留到 #2 通过之后——如果作者自己都不用，找别人测是浪费。

### 一句话总结

**代码骨架可用，探针定位正确，但当前的测量装置测不出它想测的东西。**
先花 1-2 天把四条假门标准接上真实的观测路径（尤其第 3 项的候选池快照，它是唯一能防止假阳性的防线），
再跑两周。否则两周后拿到的会是一份"四条全过"的报告，而它可能是全假的——
那比一份"四条全不过"的报告危险得多。
