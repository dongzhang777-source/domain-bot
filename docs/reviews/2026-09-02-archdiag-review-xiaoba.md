## 二、专节：§1.3 / §2.1 稳态算术独立重推

本节回应工单「必做验证 2」的四问。推导全程给出，可被任何人逐步复核。

### 2.0 先钉死管线语义（读码确认，非采信报告）

`src/index.ts` 的 `runOnce` 顺序（`src/index.ts:46-136`）：

| 步 | 位置 | 语义 |
|---|---|---|
| 采集 | `:55-65` | `collected` = 各源返回条数之和 |
| 去重 | `:67-68` | `dedupe(collected, store.knownIds())` —— **对归档已知 id 精确屏蔽**（`src/collector/dedupe.ts:39-55`，精确 `id` 集合匹配） |
| 相关性 | `:69` | `filterRelevant` ≥1 关键词（`src/refinery/filter.ts:5-8`）→ **这就是落盘字段 `relevant`** |
| 打分 | `:71-72` | HeuristicScorer |
| 阈值 | `:79-83` | **用原始分 `s.valueScore >= 0.45` 过滤** → `passed` |
| 排序 | `:87-92` | 加权分 + 新颖性（只影响排序，不影响过滤） |
| 配额 | `:94-103` | `perSourceCap = max(2, ceil(6/2)) = 3`、总上限 6 → `pushed` |
| **candidates** | `:105` | `ranked.map(r => r.entry)` —— **配额截断前的全量** |
| **原始分序列** | `:106` | `rawScores = ranked.map(r => r.raw)` —— **只覆盖 candidates，不覆盖 relevant 全体** |
| 入档 | `:119` | `store.recordItems(candidates, now)` —— **全量入档**（`src/memory/store.ts:131-159`） |

**裁定 ①：派单方所述管线语义逐字成立。** `relevant` 是去重后的残留池，`candidates` 是其中过阈值者，`rawP50/rawTop1/saturationRate` 只覆盖 candidates。

### 2.1 反推新鲜相关池（两轮独立闭合）

记号：`A_t` = 第 t 轮开始时归档条数；`R_t` = 第 t 轮 feed 中通过关键词过滤的条目集（**新鲜相关池**）；`C_t` = `R_t` 中过 0.45 阈值者。

**第一步：证明 `A_1 = 0`。**
四轮 candidates 之和 = 647 + 1 + 3 + 0 = 651，恰等于归档总量 651；且归档 651 条 `hitCount` **全部为 1**（实测 `{1: 651}`），说明每一条都是某轮的**新**候选，无一条是被第二轮重复计入的。故轮 1 开始时归档为空。✔

**第二步：由两轮独立反推 `|R|`。**

```
轮3: relevant = |R_3| − |R_3 ∩ A_3| = 341 ,  A_3 = 648  →  |R_3| = 989
轮4: relevant = |R_4| − |R_4 ∩ A_4| = 338 ,  A_4 = 651  →  |R_4| = 989
```

两轮相隔 13 分钟、独立观测，推得**完全一致的 989**。这是本推导的主要交叉验证。

**第三步：由 `candidates_4 = 0` 反推 `|C|`。**

```
candidates_4 = |C_4| − |C_4 ∩ A_4| = 0  →  |C_4| = |A_4| = 651
```

即 651 条归档在轮 4 时**全部仍在 feed 中且仍通过阈值**（否则 relevant_4 不会恰好等于 `989 − 651`）。

**第四步：新鲜池通过率。**

```
通过率 = |C| / |R| = 651 / 989 = 65.82%
```

**第五步：构造性交叉验证（印证派单方预判）。**
`|R| − |C| = 989 − 651 = 338`，正是 `relevant_4` 的全部 338 条，而 `candidates_4 = 0` → 这 338 条**全部低于 0.45**。查公式（`src/refinery/scorer.ts:30-32`）：

```
f(1,0) = 0.25 + 0.5·√(1/8) + 0           = 0.4268  < 0.45   ← 不通过
f(2,0) = 0.25 + 0.5·√(2/8) + 0           = 0.5000  ≥ 0.45   ← 通过
f(1,1) = 0.25 + 0.5·√(1/8) + 0.25·√(1/6) = 0.5289  ≥ 0.45   ← 通过
```

→ 通过 0.45 的充要条件是 **k≥2，或 (k=1 且 s≥1)**。故那 338 条在构造上正是「恰好命中 1 个关键词、0 个信号词」的条目，它们**永远不会**通过阈值。**派单方「341 条 relevant 几乎全是构造上低于阈值的陈旧残留（k=1,s=0 → 0.427）」完全成立。**

### 2.2 报告 0.88% 的错在哪：分母口径

报告取 `3 / 341 = 0.88%`。分母 341 是**去重后的残留池**——它已经被「减去 648 条已归档候选」处理过，池子里本来就不该剩下几个能过阈值的（剩下的 338 条构造上就是 k=1,s=0）。

**0.88% 测的是「归档吃剩的残渣里还有多少漏网的」，不是「新鲜内容有多少能过」。** 正确的分母是新鲜池 989。

| 口径 | 分母 | 分子 | 通过率 | 含义 |
|---|---|---|---|---|
| 报告 | 341（去重后残留池） | 3 | **0.88%** | 残渣漏网率，**非稳态通过率** |
| 正确 | 989（新鲜相关池） | 651 | **65.82%** | 新鲜内容通过率 |

> **裁定 ②：派单方量化成立，且可精确化到 65.82%。** 报告 §1.3「稳态通过率 0.88%」是分母口径错误，须整段重写。

### 2.3 报告「稳态每天约 3 条」的错在哪：把 70 分钟窗口当成日节奏

`|C|` 在四轮间是增长的：`647 → 648 → 651 → 651`（由 `candidates_t + A_t` 得出）。即 70 分钟内 feed 净增 4 条合格条目（`bySource` 显示：轮 2 的 +1 来自 `exa-llm-news`，轮 3 的 +3 = `exa-llm-news` 1 + `github-new-llm-tools` 2）。

**这 4 条不能外推为日增量**——`github` 的 `per_page=15` 与 `exa` 的 `numResults=8` 都是**饱和型小集合**（归档中 github 已 14/15、exa 已 6/8）。真正决定日产量的是 arXiv 的轮换行为，而报告从未核实它。

**外部只读实测（本审新增，可复跑）：**

```
curl -s -A 'domain-bot/0.1' 'https://export.arxiv.org/rss/cs.AI'
→ HTTP 200，942,343 字节，读取时间 2026-09-02 17:29 EDT
```

| 测量项 | 实测值 |
|---|---|
| feed 条目数 | **445** |
| `<pubDate>` 日期分布 | **全部为 2026-09-02（单一日）** |
| 与 09-01 归档比对 | 归档中 `arxiv-cs-ai` 557 条，与当前 feed 标题交集 **仅 13 条（2.3%）** |
| **→ 21 小时内轮换率** | **97.7%** |

再对当前 feed 跑本仓**自己的** `filterRelevant` + `HeuristicScorer`（忠实复刻 `normalizeText`/命中计数/sqrt 公式，阈值 0.45）：

| 关键词集 | relevant | candidates | 通过率 |
|---|---|---|---|
| 09-01 当时配置（17 关键词，0 中文） | 365 | 286 | **78.4%** |
| 当前配置（23 关键词，含 6 中文） | 365 | 286 | **78.4%** |

（两者相同的原因：新增的 6 个中文关键词在英文 arXiv 摘要上不可能命中，故英文侧口径未变。）

**三项独立方法收敛：**

| 方法 | 通过率 |
|---|---|
| A. 09-01 归档反推（轮 3/轮 4 闭合） | 65.8%（四源混合口径，含打分偏低的 github/exa） |
| B. 09-02 实时 feed 实测 | 78.4%（arXiv 单源口径） |
| C. 报告 §1.3 | **0.88%（分母错）** |

**稳态日产量推算**：arXiv 单源即 **286 条/天**，加 `huggingface-blog` / `github` / `exa` 增量约 **290–300 条/天**。

> **裁定 ②续：**
> - 「稳态每天约 3 条」——**不成立**，实测 ≈286–300，是报告值的 **~95 倍**。
> - 「低于 `maxPerDigest=6`，每天都推不满」——**方向相反**。候选/推送位 ≈ 286:6 ≈ **48:1**，是**严重过剩**，不是推不满。
> - 「比 D 在 `review-2026-09-02-external.md:303` 估的『个位数到几十』低一个量级」——**方向相反**，实测比 D 的估计**高**一个量级。
> - 「末轮 candidates=0，I-1 已走到 1/3」——**不能外推到日节奏**。那个 0 是**同一天 70 分钟内连跑 4 轮**的产物（该窗口 feed 只净增 4 条），不是日节奏稳态。日节奏下每轮 candidates ≈ 286。

### 2.4 裁定 ③：A′1 定性为「开跑前阻断项」是否成立

**机制成立，后果不成立，故定性不成立。**

| | 报告主张 | 本审裁定 |
|---|---|---|
| 机制 | A3 全量入档 → 候选池退化为纯新增流 | ✅ **成立**（§2.0 管线 + §2.1 反推，算术闭合） |
| 后果 | 池枯竭 → 每天仅 3 条 → 推不满 → I-1 触发 | ❌ **不成立**（feed 日轮换，日新增 ≈286 条） |
| 定性 | 开跑前阻断项 | ❌ **不成立**，建议降级 |

**降级后的正确处理**：A′1 案 A（重置 `memoryDir`）仍可作为**低成本的数据整洁选项**保留——但它现在的理由必须改写，从「解除枯竭」改为「让 14 轮序列从空归档开始、完全同构」。注意降级后**案 A 的缺点不再可忽略**：它会丢掉 651 条基线数据（报告中 justification 的「实际损失接近零」依赖的是 `hitCount` 全 1，这在日节奏下仍然成立，但「零代码改动」的优势要对抗「丢失基线」的代价重新权衡）。

> **一条不应被忽略的连带影响**：过剩取代枯竭后，探针的实际形态从「推不满」变成「每天从 ~286 条里挑 6 条」。这意味着 👍率测的是**头部 6 条的选择质量**，而不是 feed 的整体质量。这符合探针目的（测「用户要不要这个筛选结果」），但**两周后的结论措辞必须据此调整**——不能说「用户喜欢这些内容」，只能说「用户喜欢这套筛选挑出来的内容」。建议补入 §五 或 §六 Q3。

### 2.5 裁定 ④：A′1 验收判据「连跑 ≥4 轮每轮 candidates>0」会假红吗

**会，而且与 feed 空窗无关——问题出在判据本身没定义轮间隔。**

在「候选池 = 纯新增流」的机制下，若 4 轮在**短时间内连跑**（现成先例：现有 4 轮的间隔是 29 秒 / 56 分 / 13 分），那么第 2 轮起每轮只剩 feed 在间隔期内的增量。**即使重置归档，连跑第 4 轮仍极可能为 0**——实测序列 `647 → 1 → 3 → 0` 就是这一机制的直接演示。

→ **必改**：A′1 验收判据必须写明轮间隔（建议「≥1 天，模拟真实探针节奏」）或改为「每轮之间 feed 存在新增」。否则该判据在「连跑」的字面语义下**几乎必然假红**。

**另外——feed 空窗日的假红风险真实存在，但归属 I-1 而非 A′1：**

外部查证（arXiv 官方 `info.arxiv.org/help/availability.html`，2026-09-02 读取）：

> 「Submissions to arXiv are typically posted publicly **Sunday through Thursday**, with **no announcements Friday or Saturday**.」
>
> 公告时间表：周一 14:00–周二 14:00 收稿 → 周二 20:00 ET 公告；……；周五 14:00–周一 14:00 收稿 → 周一 20:00 ET 公告。
>
> 2026 假日顺延名单含：**Monday 2026-09-07**（Labor Day，距今 5 天）。

**后果**：arXiv 周五、周六无新公告 → 每日 1 轮时，**周五、周六连续两天 arXiv 零新增**；若再叠加 09-07 劳工节顺延，可达 **连续 3 天零新增 → I-1 触发 → 判「探针无效」**，而真因是 arXiv 的排班，不是仪器故障，也与需求无关。

**缓解因素（须同时说明，避免夸大）**：`github-new-llm-tools` 的 `{{since_days:7}}` 窗口逐日滑动（`bc8be33`）、`exa` 是实时检索，二者在 arXiv 空窗日可能补上非零候选。**故 I-1 是否假红取决于非 arXiv 源在空窗日的补充能力——这个量未测量。** 但「未测量」不等于「无风险」：I-1 的 N=3 与「每天 1 轮」的组合，恰好落在 arXiv 排班造成的可预期空窗长度上，这在签字前必须处置。

> **裁定 ④**：A′1 验收判据缺轮间隔定义 → **必改**；I-1 阈值 N=3 未经标定且存在可预期假红窗口 → **新增必改（见 M6）**。

### 4.2 A′4 案 A（阈值下调 0.90）——过不了它自己的验收判据

A′4 的独立红灯写着：「先写断言『**存在原始分 ≥ 新阈值的真实条目**』，在 0.99 下必红」。

用今日实时 feed（n=365 候选）实测这条断言：

| 阈值 T | ≥T 条数 | 占比 | 断言「存在」 |
|---|---|---|---|
| 0.99（现状） | 0 | 0.00% | 🔴 红 |
| **0.90（案 A）** | **0** | **0.00%** | 🔴 **红——验收不通过** |
| 0.85 | 1 | 0.27% | 🟢 绿 |
| 0.80 | 9 | 2.47% | 🟢 绿 |

**→ 案 A 把 0.99 改成 0.90，全池达标数仍为 0，验收断言仍红。案 A 不构成有效修复。**

更根本的问题在**判据形式**：「过半候选 ≥ T」在原始分分布（P50≈0.571、P90≈0.733、Top1≈0.860）下近乎不可用：

- `T > Top1(0.860)` → `saturationRate` 恒 0（**死**）；
- `T ≤ P50(0.571)` → `saturationRate` ≥ 0.5 → **每轮触发，立刻判「探针无效」**；
- 唯一能落在 (0, 0.5) 区间的 `T ∈ (0.571, 0.860]`，且随 T 接近 P50 而急剧趋近 0.5——**可用带宽极窄且不稳定**。

> 报告倾向案 B（换 P90 指标）是对的，但理由（「与 X2 最一致」）偏软。**硬理由是：案 A 不是次优，是无效——它连 A′4 自己写的验收断言都过不了。** 建议在 §7.8 决策点 7 中直接删除案 A，或标注「实测不满足 A′4 验收判据，不可选」。
