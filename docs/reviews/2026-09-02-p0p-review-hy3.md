## 二、评审问题

### Q1. D 的三票否决是否真正闭合？

- **V1（长驻 store 陈旧）**：**闭合。** 根因（receiver 持有跨进程 store）已移除，每回调从盘重建。本人探针 + lifecycle 测试双重验证 `recorded`。
- **V2（守卫防不住摘链）**：**基本闭合，余文本守卫天花板。** 新增 3 条启动链守卫（runOnce 调用 / pollFeedback 调用 / `telegram && !once` 条件）。变异 `if(false)` 实测第 3 条红——即 D 演示的「删 pollFeedback 启动行」场景被捕获。但守卫本质是**文本存在性**检查，自述已如实声明天花板：若写成 `if (telegram && !once) { const f = () => pollFeedback(...) }`（定义不调用），三条守卫全绿而轮询从不启动。`lifecycle.test.ts` 提供进程级补位，但**未覆盖「main 的 do/while 真的 invoke 了 pollFeedback」**这一运行时可达性。属残余盲区，非否决级。
- **V3（观测自证污染）**：**三项盲区修复两项，剩一项。** 盲区1（skippedSources 不落盘）已修（末行可见）。盲区3（saturation 用加权分误报）已修（代码改原始分）。盲区2（P50/Top1 记加权分→闭环自证）以「新增 rawP50/rawTop1 作真值读数」**缓解**——`candidateP50` 仍记加权分，但判据明确「混淆即作废」，仪器已能区分。**盲区4（源活但结构性零产出，第三类失败）未触及**：仍无字段/测试区分「源挂（skippedSources）」「池枯竭（fetch 成功无新）」「活但被 isRelevant 全滤」。新增的 `relevant/isNewRate` 仅间接辅助。

**可证伪反对**：若有人说「V2 已彻底闭合」，反例是上述「定义不调用」形态守卫全绿——故只能说「针对 D 演示的具体失败模式已闭合」。

### Q2. 新代码里还有什么「绿灯但断开 / 仪器再次失灵」？

1. **每回调 `new MemoryStore` 重读全量盘（开销）**：`receiver.ts:34` 每次回调同步读 archive.json（可达 2MB+）/feedback.json/weights.json。人类反馈频率下可忽略；但高吞吐或 archive 膨胀后每次回调 O(n) 解析——**扩展性债，非正确性缺陷**。
2. **并发写竞态 / refreshWeights 哈希闸门 TOCTOU**：
   - 单进程内：`pollFeedback` 是 `await` 串行的，`processTelegramUpdate` 内 `recordFeedback`→`refreshWeights` 全程同步无 `await` 间隙，`refreshWeights` 又是同步函数——**单实例下无 TOCTOU，闸门原子**。D 原「长驻冻结」假设此前已自撤，本次同向。
   - **真实残险在「多实例」**：若同 `memoryDir` 起两个进程（`npm run loop` 两次，或 loop + `--once` 定时），各进程 `load()` 全量后 `save*()` 全量覆盖 → **last-writer-wins，feedback.json 可能丢条目、weights.json 回退**。当前 `index.ts:231` 仅以 `argv[1].endsWith('index.js')` 隐式守卫，无单实例锁。建议加 pidfile/文件锁。属于潜伏 footgun，当前单实例探针不触发。
3. **`candidateP50/P90/Top1/pushedMean` 仍记加权×新颖性分**：与 raw 并存，依赖操作员「自觉看 raw」。`probe-verdict-criteria.md §4` 已写死「混淆即作废」，但若有人直接读 candidateP50 仍会自证。建议未来把加权分移出主判据或加醒目注释。
4. **盲区4无仪器**：同上，第三类失败模式仍混在「健康零产出」里。

### Q3. `probe-verdict-criteria.md` 判定线漏洞？

- **未定义中间地带**：§0 自己提出「中间地带怎么办」却未作答。P-* 要求「同时满足」才通过，G-* 任一即失败，但**既未通过也未失败**（如 P-1 达、P-2 未达、无 G-* 触发）时文档无处置规则——结构性洞。
- **I-/G-/P- 触发冲突无优先级**：例如 I-2（无效）与 G-2（失败）可同时触发，谁优先未定义。
- **I-2 阈值（反馈率<10%）可能偏高**：被动消费者主动点击率常远低于 10%，易把「正常低互动」误判为「仪器失效」，可能过早 abort 探针。
- **G-1/G-3 的「主动消费性查看 / 主动打开」无测量机制**：只说「调试性打开不算」，但**没有遥测方案**界定「主动」。主观口径 + D 已警示「手抄数据不可信」——判定线赖以成立的输入本身不可客观验证。
- **P-4 定性证据（推送实际影响工作决策）靠操作员自述**：正是 D §七.1 批判的「手抄/自报」信任模型，重新引入同一风险。
- 结构上这些都**不阻断 P0' 修复验收**，但属于「仪表刻度未定死就开跑」的 P-1 级遗留，与 D §七.2 一致——开跑前老张必须签字定稿。

### Q4. 无限定区：更要紧的话

**P0' 修的是「仪器是否正确」，但探针能否验证产品命题仍取决于「真实反馈是否流过」——而它至今为零。**
证据：`docs/evidence-latest.md` 与 observations 末行均 `feedbackCount: 0`。自 D 评审至今，两轮真实运行、**75 个测试**，仍**零条真实 👍/👎 落盘**。所有「进化回路」代码仅被**测试**驱动（本人的 up/down 探针也是测试，非真人点击）。

这与 D 的「硬阻断 2/3」同源：
- 反馈入口只在 `telegram && !once==false`（常驻+有 token）下启动；无 token 时 `--once` 仅打印「下次常驻入账」却无 daemon 接收——**无 key 即无输入通道**。
- 即便修通，两周能否得出「用户要不要一万个 bot」仍受 D §五 的长度偏倚 + §六 统计功效不足约束（每源约 12 次反馈，±0.15 权重漂移，无法区分偏好与噪声）。

**故本验收的范围是「P0' 代码修复是否真修通」——是；但「探针现在能开跑并证伪产品命题」——否，仍缺 Telegram key + 真人点击 + 签字的判定线。** 这条边界比任何代码 bug 都更要紧，必须在总判断里写死，以免「75 全绿」被误读为「回路已验证有效」。
