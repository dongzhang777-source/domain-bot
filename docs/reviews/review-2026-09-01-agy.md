## 定向问题逐条回答

### Q1. 探针逻辑本身：一个 bot + 一个用户 + 两周，能否为"千 bot 需求"提供有效证据？

**结论：有条件同意。能提供 *方向性* 证据，但不能提供 *需求规模* 证据。**

**理由：**

探针设计的核心假设链是：**单人真实使用 → 信息价值可验证 → 推广到千人千 bot**。这条链在前两环是成立的——你能验证"AI 帮我盯一个领域"这个动作本身是否有价值、自进化是否可感知。但它在第三环（千 bot 需求）上存在逻辑跳跃：

- **单人验证的是"供给侧可行性"（能不能做出有用的 bot），而非"需求侧规模"（有多少人愿意用）**。即使探针通过全部四条线，你也只能说"技术上可行、对 AI 从业者有价值"，不能说"有千人级需求"。
- 假门检验在产品方法论中通常要求**多个独立用户的行为数据**。单人单领域的通过只能算 *信号*，不算 *证据*。

**通过线评估：**

| 指标 | 评估 |
|---|---|
| 主动查看 ≥ 10 次 / 2 周 | **偏松**。作者是设计者，出于好奇心和调试需求就会查看远超 10 次。建议区分"主动消费性查看"与"调试性查看"，只计前者。 |
| 👍 率 ≥ 30% | **合理偏紧**。前提是反馈机制真的上线（当前 Telegram 按钮缺 token）。若只有文件推送而无 inline 按钮，反馈成本太高，率会虚低。 |
| 第 3 轮起噪音可感知下降 | **无法量化**。"可感知"是主观判断，且作者同时是评判者。建议补一个客观指标：第 3 轮后 👍 率是否显著高于前 2 轮（Fisher 精确检验 p < 0.1）。 |
| 可复制性：改 config 无需改代码 | **可验证**。当前实现确实支持——加个新领域只需写 `domain.json` + `sources.json`。但有一处硬编码：`HeuristicScorer` 的信号词表是 AI/ML 领域特定的（`sota`, `benchmark`, `outperform`...），换领域需要换信号词，这不在 config 里。 |

**可证伪的反对意见：**

> "你不需要千人数据来验证千 bot 假设——只要单人场景足够 compelling，千 bot 只是基础设施复制问题。"
>
> 反驳：SaaS 历史上"对创始人有用但无人愿付费"的产品不计其数。复制问题不是需求问题。

### Q2. 自进化的技术路线：Beta(1,1) + 步长 0.2 的天花板在哪？

**结论：在当前探针规模（2 周、单用户）下足够稳健。天花板在"维度单一"而非"数学不收敛"。**

**理由：**

数学层面，Beta(1,1) 后验均值（Laplace 平滑）是 Bayesian 更新的教科书做法，在小样本下远优于 MLE。EMA 步长 α=0.2 的含义是：每次更新只向目标移动 20%，5 次反馈后权重才移动约 67%（$1 - 0.8^5 \approx 0.67$）。对于每周几十次反馈的信号量，这个速度是合理的——不会因一次误点翻转权重，但 2 周后（假设每源 5-10 次反馈）足以产生可观测的分化。

实际验算：

- 假设 arXiv 获得 8👍 2👎，Beta 后验均值 = $(8+1)/(8+2+2) = 0.75$
- 初始权重 0.5，经 $\alpha=0.2$ 更新后：$0.5 + 0.2 \times (0.75 - 0.5) = 0.55$
- 第二次更新（假设同比例持续）：$0.55 + 0.2 \times (0.75 - 0.55) = 0.59$
- 5 轮后趋近 0.70 左右

**这是符合预期的温和收敛。**

**天花板所在：**

1. **只有一个进化维度（源权重）**。用户反馈"👎 噪音"时，系统不知道是"这个源不好"还是"这个话题我不关心"还是"这条已经看过了"。三种原因被压缩成一个信号，对源权重的归因是有噪声的。
2. **无主题级进化**。系统不会学到"我对 quantization 更感兴趣、对 benchmark 不太关心"。关键词列表是静态的。这限制了"自进化"的体感上限——用户会觉得"噪音少了一点"但不会觉得"越来越懂我"。
3. **反馈粒度是簇级而非条目级**。一个簇可能包含 3 条，用户 👍 的是代表作，但其他两条可能来自不同源。反馈被均匀归因到所有条目的源上，存在稀释。

**可证伪的反对意见：**

> "2 周后信号量太小，权重分化不可能显著到'可感知'。"
>
> 回应：以 6 簇/轮、每日 1 轮、每轮 50% 反馈率计算，2 周约 42 次反馈。分配到 7 源后每源 ~6 次，Beta 后验的 95% 可信区间宽度约 ±0.25——确实不窄。但进化的可感知性不仅来自权重数值，也来自去重和新颖性检查的累积效果（旧闻逐渐被过滤）。建议在探针日志中分别记录这两个维度的贡献。

### Q3. 启发式打分冷启动：arXiv 偏袒 + 配额硬压的坑

**结论：当前方案有一个比"arXiv 偏袒"更大的坑——打分公式的分辨力不足。**

**理由：**

启发式打分公式：$V = \min(1.0,\ 0.3 + 0.15 \times kw + 0.12 \times sig)$

问题在于：

1. **底分 0.3 太高**。任何通过关键词过滤的条目（至少命中 1 个关键词），得分最低为 $0.3 + 0.15 = 0.45$。经源权重放大（$\times (0.5 + w)$，$w$ 初始 0.2\~0.6），有效分范围为 $0.315 \sim 0.675$。而入选阈值为 $0.45 \times 0.5 = 0.225$。**这意味着几乎所有通过关键词过滤的条目都能入选**，打分器退化为"关键词过滤 + 按命中数排序"，失去了区分价值高低的能力。

2. **信号词表是领域锁定的**。`['release', 'benchmark', 'sota', ...]` 这些词是 ML/AI 圈的特有信号。换到金融、医疗、游戏领域时，这套信号词完全失效。可复制性声明（Q6）在这里被打了折扣。

3. **每源配额是对的但阈值不对**。`perSourceCap = max(2, ceil(maxPerDigest / 2)) = max(2, 3) = 3`——6 个推送位里单源最多占 3 个，还是太松。建议改为 `max(1, ceil(maxPerDigest / sources.length))` 或硬设为 2。

4. **真正的大坑：LLM 打分切换时的断层**。当 LLM 打分器接入后，分数分布会发生不连续跳变。LLM 分数和启发式分数不在同一尺度上。如果权重系统在启发式阶段积累了 prior，切换到 LLM 后源权重的含义会被污染。建议切换时 **reset 所有源权重到 0.5**，或者在切换时引入一个分数校准层。

**可证伪的反对意见：**

> "底分 0.3 不是问题——反正有配额和排序兜底，不需要靠分数做精细区分。"
>
> 回应：如果打分的唯一作用是排序，那打分器可以简化为关键词计数器。但这样"价值分"就失去了语义，探针无法验证"推送的东西真有价值"这一假设——因为你无法区分"关键词多的高分"和"真正有价值的高分"。

### Q4. 渠道策略：排除登录态通道的信息质量伤害

**结论：对 AI/LLM 领域，伤害可控。对其他领域，可能致命。**

**理由：**

AI/LLM 领域的高价值信息源恰好集中在开放生态：arXiv（开放获取）、HuggingFace（开源社区）、GitHub（公开仓库）。Twitter/Reddit 的增量价值主要是"社区讨论热度"和"早期泄露/传闻"，这些信息在 arXiv 上线后 24-48 小时内会被正式渠道覆盖。

**但对其他领域（如消费电子、金融、娱乐），Twitter/Reddit/小红书可能是唯一的实时信号源**。如果探针的可复制性声明（"改 config 就能换领域"）要成立，渠道策略的局限性需要提前声明。

**两全方案建议：**

1. **只读 API + 短寿命 token 方案**：Reddit 有只读 OAuth 接口（`read` scope），风控比 scraping 宽松得多。Twitter/X 的 Basic Tier API (\$100/月) 提供 10k 推文/月的只读获取。这些都不需要模拟登录。
2. **Nitter / 镜像方案**：但 Nitter 实例 2025 年起大面积下线，稳定性堪忧。
3. **代理人方案**：不抓取原始平台，而是通过 Exa 语义搜索间接获取平台内容的摘要/讨论。当前 Exa 源已部分起到这个作用。

**可证伪的反对意见：**

> "排除 Twitter/Reddit 会导致错过重大事件的早期信号，使探针产出的信息始终滞后 24-48 小时，用户会因此判定 bot 无价值。"
>
> 测试方法：在探针运行期间，手动记录 5 个 Twitter 首发的重大事件，检查 bot 是否在 48 小时内通过其他渠道覆盖了同一事件。若覆盖率 < 60%，则渠道策略伤害显著。

### Q5. 防自我固化：删除 ε-greedy 后还有什么风险？

**结论：当前机制在源维度上防固化做得不错，但在内容维度上存在"关键词回音室"风险。**

**理由：**

已有的防固化设计（好的方面）：

- ✅ 无反馈源权重向 0.5 先验回归（不会被误杀）
- ✅ 全量抓取所有 enabled 源（删除 ε-greedy 是正确的——低权重源的"探索"不应该靠跳过高权重源来实现）
- ✅ 记忆库 2000 条 FIFO 裁剪（旧记忆自然遗忘）
- ✅ 人工可修正 JSON

残余风险：

1. **关键词过滤是硬边界**。不在 `domain.keywords` 中的内容会被 100% 过滤掉，永远无法进入推送。如果领域发生概念漂移（比如从 "LLM" 转向 "world model" 或 "test-time compute"），系统无法自适应。**关键词列表需要人工定期维护**，这在"无人值守"承诺下是个矛盾。

2. **新颖性检查的 Jaccard 0.7 阈值可能误杀变体**。标题仅有细微差异的后续报道（如 "GPT-5 发布" vs "GPT-5 发布后 24 小时的社区反应"）Jaccard 可能 > 0.7 被判定为旧闻。这不是"固化"，但会导致系统错过有价值的跟进信息。

3. **打分器信号词的固化**。`HeuristicScorer` 的信号词是硬编码的，不会随反馈进化。如果用户持续 👎 含 "benchmark" 的推送，源权重会下调，但信号词加成不会消失。

4. **归档膨胀导致新颖性误判**。2000 条归档中如果某些高频词（如 "transformer"）在大量标题中出现，新条目只要包含 "transformer" 就可能与多条历史条目产生中等 Jaccard（0.5\~0.7），虽不触发旧闻阈值，但会导致 `isNovel` 遍历开销增长。这不是 bug，但在 2000 条规模下 $O(n)$ 遍历的性能值得关注。

**可证伪的反对意见：**

> "关键词回音室不是问题——用户本来就只想看这些关键词，领域漂移时用户自然会去改 config。"
>
> 回应：如果用户需要手动更新关键词才能跟上领域变化，那"自进化"的故事就不完整。至少应该在推送中偶尔包含"边缘相关"内容（比如命中 0 个关键词但 Exa 语义搜索返回的条目），让用户有机会通过 👍 拓宽系统视野。

### Q6. 可复制性声明："无数个 bot 就可以跑通"离现实还差什么？

**结论：差两件事——信号词泛化 和 源注册表模板化。核心框架已具备可复制性。**

**具体差距：**

| 维度 | 现状 | 缺口 |
|---|---|---|
| 关键词配置 | ✅ `domain.json` 可换 | — |
| 源注册表 | ⚠️ `sources.json` 可换，但需要知道领域对应的 RSS 源、搜索 query | 缺少"领域 → 推荐源列表"的引导或模板 |
| 启发式信号词 | ❌ 硬编码在 `HeuristicScorer` 中 | 应移入 `domain.json` 或按领域分 profile |
| 采集适配器 | ✅ 6 种通道覆盖广 | 某些领域可能需要专属适配器（如金融需要 SEC EDGAR） |
| 打分阈值 | ⚠️ 固定 0.45 | 不同领域信息密度不同，阈值应可配置（已经在 config 里，✅） |
| Telegram 推送 | ⚠️ 需要用户自建 bot + 获取 chat ID | 缺少 setup 向导 |
| LLM 打分提示词 | ⚠️ 提示词中领域描述取自 `domain` 字段名 | 建议在 `domain.json` 中增加 `description` 字段供 LLM 参考 |

**最关键的一条**：当前 `HeuristicScorer` 的信号词（`sota`, `benchmark`, `open source`...）是 AI 领域特定的。如果不把信号词配置化，"改 config 就能跑新领域"这句话就是假的。修复成本很低（把 `signals` 从类属性移到 `DomainConfig`），建议在探针期间就改掉。

**可证伪的反对意见：**

> "可复制性在探针阶段不重要——先验证单领域价值，可复制性是工程问题不是产品问题。"
>
> 回应：同意优先级排序。但可复制性是假门四条线之一。如果探针结束时发现信号词需要领域专家手工调参，这会大幅提高千 bot 的运营成本，从而影响商业可行性判断。

### Q7. 两周后的决策框架

**结论：给出三级判据如下。**

#### 🟢 加大投入（千 bot 路线值得推进）

**全部**以下条件满足：

- 主动消费性查看 ≥ 10 次（排除调试性查看）
- 👍 率 ≥ 30%（前提：Telegram 反馈按钮上线，否则此指标无效）
- 第 4 轮后 👍 率显著高于前 2 轮（方向正确即可，不要求统计显著）
- 至少有 1 次探针推送的信息直接影响了作者的工作决策（定性证据）
- 加第 2 个领域验证可复制性，无需改代码（信号词配置化后）

**加大投入的下一步**：招募 3-5 个非作者用户（AI 从业者同行），各自配置领域跑 2 周，收集多人数据。

#### 🟡 改设计后值得重跑

**以下任一**条件出现：

- 查看次数达标但 👍 率 < 30%：说明用户有"盯领域"需求但推送质量不够 → 优先接入 LLM 打分后重跑
- 👍 率达标但查看次数 < 10：说明推送质量可以但分发渠道不对（文件推送不够 push） → 优先接入 Telegram 后重跑
- 自进化不可感知但其他指标通过：说明 2 周信号量不够 → 延长到 4 周或增加反馈粒度（条目级而非簇级）
- 可复制性验证失败（换领域需改代码）：先修代码再声明可复制

#### 🔴 放弃（千 bot 路线证伪）

**以下任一**条件出现：

- 查看次数 < 5 且 👍 率 < 15%：作者自己都不用，需求假设不成立
- 2 周内探针推送的信息从未影响任何实际决策：说明"盯领域"是伪需求或 bot 远不如人工浏览
- 作者发现自己更倾向于直接刷 Twitter/HN 而非看推送：说明 bot 的价值主张（节省注意力）不成立

> [!IMPORTANT]
> **反自我欺骗保护**：建议在探针启动前，让一个不了解项目的第三方记录作者当前的信息获取习惯（每天花多少时间刷 AI 资讯、主要渠道是什么）。2 周后对比：如果作者的信息获取行为没有发生可观测的变化（比如刷 Twitter 的时间没有减少），即使 👍 率达标，探针也应判定为"有趣但不改变行为"——这不足以支撑千 bot 投入。

## 无限定问题（自由发言）

### 1. 最大的系统性风险不在技术层面

你的代码写得很好——依赖注入设计使 100% 离线测试成为可能，优雅降级策略使零配置也能跑，Beta 平滑的数学选择正确。35/35 测试绿。**但这恰恰是最危险的地方。**

技术上的"完成感"会让你高估产品价值。代码质量和用户价值之间没有因果关系。我见过（在训练数据中）太多"技术优雅但无人使用"的项目。你的偏见声明 §1 已经指出了这一点，但我想加重强调：**测试全绿不是跑探针的理由，用户行为数据才是。**

### 2. "自进化"的感知可能比"自进化"的事实更重要

用户（包括你自己）是否"感觉"到 bot 越来越懂你，取决于两件事：

- **噪音的下降**：这主要来自去重和新颖性检查的累积效果，而非源权重的移动。如果你把"噪音下降"归因于"自进化"，因果关系其实是错的。
- **精准度的上升**：这需要主题级学习（目前不存在），或者关键词列表的人工迭代。

建议在探针日志中分开记录："本轮过滤了 X 条旧闻"（去重贡献）vs "本轮源权重调整使排序变化了 Y 位"（进化贡献）。这样探针结束时你能区分两者的贡献度。

### 3. Telegram 反馈按钮是探针的关键路径

当前状态：Telegram 按钮缺 token，未上线。但 👍 率 ≥ 30% 是四条通过线之一。**没有 Telegram 按钮，这条线无法验证**。文件推送 + 人工记录反馈的摩擦太大，会严重低估真实反馈率。

**建议在探针正式启动前，把 Telegram bot 创建和 token 获取作为 Day 0 任务完成。** 这是 5 分钟的事情（@BotFather），不应该成为阻塞项。

### 4. 缺一个 Telegram 回调接收服务

审计发现：代码中有 `sendDigestTelegram`（发送）和 `parseCallbackData`（解析回调），但**没有 Webhook server 或 Long Polling 守护进程来接收 Telegram 的回调事件**。即使 token 到位、按钮上线，👍/👎 按钮按下后目前无法被系统接收和处理。

这是一个功能缺口，不是降级——测试中 mock 了回调流程所以全绿，但真实环境中反馈闭环是断开的。

### 5. 归档容量与 isNovel 性能

`MemoryStore.isNovel()` 对每个候选条目遍历全部归档（最多 2000 条）计算 Jaccard。每轮 \~960 个候选 × 2000 个归档 = 192 万次 Jaccard 计算。虽然 Jaccard 本身是集合操作（$O(|A| + |B|)$），但在 V8 中 Set 的交并操作有常数开销。当前规模下可能耗时数秒，不会 block，但如果归档增长或候选量增加，这里会成为瓶颈。

建议：用 MinHash/LSH 做近似去重预筛，或者对归档建倒排索引（token → entry IDs），只对共享 token 的条目对计算 Jaccard。

### 6. 跨项目关联观察

本探针（domain-bot）与 `fati-server` 的"千 bot 工厂"路线直接相关——探针通过 → 千 bot 进入 fati-server 的优先级队列。建议在探针结果归档时，同步更新 `fati-server` 的需求文档（`需求 50` 的状态从"待验证"变为"已初步验证/证伪"）。

另外，domain-bot 的 Agent-Reach 集成（Exa/V2EX/B站/Jina）与 `fati-server` 的全渠道采集管线可能存在代码复用机会。如果探针通过，适配器代码应考虑抽取为共享 package 而非复制粘贴。

## 总判断

### **改设计后值得跑完两周。**

具体来说，在正式启动探针前需要完成以下 **3 项前置修复**（预计半天工作量）：

1. **创建 Telegram Bot + 获取 Token**：使反馈闭环可用，否则 👍 率指标无法验证。
2. **实现 Telegram 回调接收**（Webhook 或 Long Polling 最小实现）：否则反馈数据无法进入系统。
3. **将 HeuristicScorer 的信号词移入 `domain.json`**：否则可复制性声明无法验证。

以下为 **建议但非阻塞** 项：

- 在探针日志中区分"去重贡献"与"权重进化贡献"
- 记录作者的基线信息获取习惯（用于 2 周后对比）
- `perSourceCap` 收紧到 2
- 启发式打分底分从 0.3 降到 0.15，拉开分辨力
- 在 `domain.json` 中增加 `description` 字段供 LLM 打分器使用
- LLM 打分器接入时 reset 源权重或引入分数校准层

**核心判断逻辑**：探针的商业假设（"AI 帮我盯领域"有真实需求）值得验证。代码实现质量足够支撑 2 周实测。但当前状态下反馈闭环断开，使得四条通过线中有两条（👍率、自进化感知）无法被可靠测量。修复成本很低，应该先修再跑。
