### 0.1 B（agy）有一处确证的证据错误

B 的报告头部声称「**memory/ 实测归档 412 条**」。实测核查：

```
archive.entries      = 29
archive.digestRefs   = 29      （两者之和 58，仍不等于 412）
archive.json 字节数   = 14600
JSON 顶层键           = ['entries', 'digestRefs']
```

且我扫了工作区内全部 JSON/MD 文件的记录数，**不存在任何含 412 条记录的文件**（最大是 `package-lock.json` 97 条）。
A 和 C 各自独立测得 **29 条**，且都给出了按源分布（`arxiv 21 / exa 5 / hf-blog 2 / gh 1 / 其余 0`）——两份独立数据完全吻合。

**裁决建议：B 的定量陈述需抽查，定性分析仍可用。** 具体地：
- B §2 的权重验算（8👍2👎 → 0.75 → 0.55 → 0.59）是纯假设推演，**不依赖 412，可用**；
- B §5 的「192 万次 Jaccard」与 A 的「190 万次」独立吻合，**可用**；
- B §Q3 的阈值算术（0.315~0.675 vs 0.225）与 C 独立算出的结果一致，**可用**。

即：412 是孤立的错误陈述，未污染 B 的主要推理链。但**它提醒我们 B 的"实测"标签不可全信**，凡 B 标注实测的数字都应与 A/C 交叉验证。

### D1 · 假门标准 #3「第 3 轮起噪音可感知下降」会怎样？【最重要的分歧】

| 方 | 判定 | 依据 |
|---|---|---|
| **A** | **假阴性**——按当前配置第 3 轮噪音是**上升**的，"这条线设了也测不到" | 节奏错配 + 候选池 278 轮耗尽 → 质量单调衰减 |
| **B** | 未直接判定，但**暗示噪音会下降**且归因于去重 | §2「噪音的下降主要来自去重和新颖性检查的累积效果，而非源权重移动」 |
| **C 初稿** | **假阳性**——噪音会下降，但归因错误 | 传送带消耗（**方向判错，已更正**） |

**裁决：三方都不完全对。实测裁定如下——**

C 复核时取到的分数序列（见 §0.2 表）显示：**连续 18 条 arXiv 推送全部触顶 1.00，逐轮 mean 变化 `+0.000/+0.000`**。

1. **A 的机制正确，结论需修正**：候选池确实在被传送带消耗，推送内容的**真实质量在衰减**（噪音客观上升）。
   但 A 假设了"打分排序 ≈ 质量排序"，推出"第 10 轮推的是第 60 名"——**实测证明这个假设不成立**：
   18 条全满分，打分器根本没排出质量顺序，所以不存在"第 60 名"，只有"RSS 里的第 60 条"。
2. **B 的归因错误**：B 说噪音下降来自"去重和新颖性检查的累积效果"，但 `isNew` **不参与排序也不参与过滤**
   （A 零节③ + C 问题6 + 实测 29/29 全标 🆕 三方一致确认）→ **B 引用的机制在运行时不存在**。
3. **C 初稿方向错误**，已更正。

### D2 · Beta(1,1) + α=0.2 稳健吗？

| 方 | 判定 | 关键论据 |
|---|---|---|
| **A** | 数学没问题，**但信号量不够喂它** | 每源两周 4-8 次反馈 → Beta 后验 std ≈ 0.12-0.15；而权重调节幅度仅 ±20%（`×(0.5+w)`，w 0.3→0.7 使有效分 ×0.8→×1.2）→ **误差与调节幅度同量级**。"路线不用改，参数要改" |
| **B** | **足够稳健**，天花板在"维度单一"不在"数学不收敛" | 验算 8👍2👎 → 后验 0.75 → 权重 0.5→0.55→0.59→5 轮趋近 0.70，"符合预期的温和收敛" |
| **C** | **不稳健**，问题在 EMA 结构 | 双重平滑里 EMA 的 α 固定；n=5 时后验 std≈0.2，权重随机游走 ±0.1，而乘数有效范围仅 0.7~1.1 → **噪声与有效范围同阶** |

**裁决：按最严 → A+C。B 的验算漏了方差。**

B 的推演（0.5→0.55→0.59→0.70）**假设了反馈比例稳定在 8:2**，算的是期望轨迹；
A 和 C 各自独立算的是**方差**，两者结论一致：A 得 std 0.12-0.15 vs 调节幅度 ±20%，C 得 std≈0.2 vs 有效范围 0.4。
**期望收敛 ≠ 可辨识收敛**——B 展示的轨迹会在实际中淹没在 ±0.13 的噪声里。

> **最优收敛点是 A 的 A7**：不要源级权重，改**条目特征权重**（关键词/信号词/内容类型）。
> 理由：样本量从"源数（7）"变成"推送条数（几十）"，学习效率高一个量级。
> **这一个改动同时化解三方分歧**——A 的采样偏差（A6）、B 的"维度单一"（B 天花板 1、2）、C 的"7 维 vs 无限内容空间"全部指向同一处。
> 且 B2 的簇级稀释也应一并修（反馈归因到条目级）。

### D3 · Jaccard 0.7 阈值：太严还是太松？

| 方 | 判定 | 依据 |
|---|---|---|
| **A** | **太严**，从未触发 → 29 条归档 100% 标 🆕，标记是纯装饰 | U4 实测 |
| **B** | **太松**，会误杀有价值的跟进报道（"GPT-5 发布" vs "GPT-5 发布后 24 小时的社区反应"） | Q5.2 推测 |
| **C** | **两阈值之间存在语义冲突带** [0.35, 0.7)：既聚成"同事件"又标"🆕增量" | 实测英文近似重复对 jaccard=0.667 落在带内 |

**裁决：A 正确，B 的担心在实测中不发生，C 是有效补充（但依据不是 B 的例子）。**

实测证据一：**29/29 条全部 `isNew=true`**（A 和 C 独立测得同一结果）
→ **0.7 阈值在真实数据上从未触发过**。

实测证据二：把 **B 举的例子直接跑一遍**（调 `dist/` 真实 `tokenize/jaccard`）：

```
B 的原例（中文）："GPT-5 发布"  vs  "GPT-5 发布后 24 小时的社区反应"
  tokens A: [ 'gpt', '发布' ]
  tokens B: [ 'gpt', '发布后', '24', '小时的社区反应' ]
  jaccard = 0.200   → isNovel(0.7) 不判旧闻 ✅   cluster(0.35) 也不聚类

同义英文改写："GPT-5 released"  vs  "Community reaction 24 hours after GPT-5 released"
  jaccard = 0.286   → isNovel(0.7) 不判旧闻 ✅   cluster(0.35) 也不聚类
```

→ **B 担心的"误杀跟进报道"实测完全不发生**（0.200 远低于 0.7）。
反而暴露了一个 B 未意识到的反向问题：**同一事件的跟进报道连聚类都聚不到一起**（0.200 < 0.35），
即"同事件合一"对这类变体失效。这**支持 A（阈值太严）而不是 B（太松）**。

> 汇总裁决依据的校正：本矩阵初稿曾称"B 的例子 jaccard 约 0.4-0.5，落在 C 指出的冲突带里"，
> **该数字未经实测，实测为 0.200/0.286，不在带内，已更正。**
> C3 的冲突带 [0.35, 0.7) **仍成立**，但依据是另一组实测数据：
> `"New LLM inference benchmark released"` vs `"Another LLM inference benchmark released"` → **jaccard = 0.667**，
> 正落在带内（会被聚成一簇，同时被标 🆕增量）。即冲突带需要标题相当相似才会触发，
> 而 B 举的跟进报道型变体相似度远低于此。

> **合并裁决**：问题不是 0.7 太严或太松，而是 **0.35 与 0.7 两个阈值语义未对齐**，
> 且**对跟进报道型变体两者都失效**（既不聚类也不判旧闻 → 同一事件的多轮跟进会被当成互不相关的独立新闻重复推送）。
> 修法：统一为单一阈值体系（如 cluster 0.5 / novelty 0.5，或让 `isNew` 直接复用 cluster 的判定结果），
> 并让 `isNew` 真正参与排序，否则删掉它并同步修改假门标准 #3 的措辞（A 的 U4 建议："一个 100% 恒真的标记比没有标记更糟"）。
> **注意**：若按 C1 修中文分词，中文场景下这两个阈值需重新标定（当前中文 jaccard 恒 0，上例的 0.200 已是因为混排了英文 `gpt` 才不为 0）。

### D5 · 打分公式怎么修

| 方 | 修法 |
|---|---|
| **A** | 关键词匹配加**词边界** + `kwHits` 按文本长度归一化（`hits / sqrt(token_count)`）——"这比每源配额更本质" |
| **B** | 底分 **0.3 → 0.15**，拉开分辨力 |
| **C** | `kwHits` 归一化（`hits / keywords.length`）或对数压缩 + 起步分降为 0 |

**裁决：A 最本质，但 C4 的实测证明「只降底分不够」，必须组合。**

**B 的修法只移动值域，不解决饱和。** C 的 `hits/keywords.length` 归一化也不解决长度偏袒
（arXiv 长摘要命中数天然高，除以固定的 17 无济于事）。

> **合并修法（推荐）**：
> 1. **A 的词边界**（修 A1 的 `rag`→`storage` 误伤）——这是硬 bug，必修；
> 2. **A 的长度归一化** `hits / sqrt(token_count)`——直击"长文本系统性得高分"根因，
>    并修正 exa 被惩罚的问题（exa 是上游语义筛选过的，arXiv 是全量未筛选，**当前打分器在惩罚已筛选、奖励未筛选**）；
> 3. **C 的起步分降为 0**——配合归一化后才有意义；
> 4. 修完后**重新标定 `scoreThreshold`**（当前 0.225 的过滤线在新公式下含义会变），
>    并按 A5 把过滤改为作用在**原始分**上、排序才用加权分（解耦"能不能出现"与"排第几"）。

### D6 · 探针能否「证实」千 bot 需求

> 👍率≥30% → 不可外推，必须补 n>1。这样探针**失败时能快速止损，成功时不会误判**——
