## 一、修复是否"真修通"而非"修绿"？

**结论：没有真修通。回路在单个函数层面接通了，在进程层面仍是断的。**

### V1：长驻轮询器持有陈旧的 store 快照（致命）

`src/index.ts:199` 在 `main()` 里构造**一个** `MemoryStore` 交给 `pollFeedback`，这个对象存活整个进程（14 天）。而 `runOnce` 每轮 `new MemoryStore()`（第 46 行），把新 ref 写进 `archive.json` 的 `digestRefs`。

`MemoryStore` **没有 reload 方法**，`archive.digestRefs` 停在进程启动那一刻。于是：

```
盘上 digestRefs = [ 'rs:0', 'rs:1' ]        ← runOnce 刚写进去的
轮询器 resolveRef('rs:0')  = undefined      ← 它看不见
processTelegramUpdate(真实回调) = 'ignored'  ← 反馈被丢弃
```

实测输出（`tests/_review-probe.test.ts` P1，验证后已删除）：

```
[P1] runOnce 注册的 ref = rs:0
[P1] 盘上 digestRefs = [ 'rs:0', 'rs:1' ]
[P1] 轮询器内存里能解析吗 = undefined
[P1] 真实回调处理结果 = ignored (recorded 才算接通)
```

**严重性：这是 v0.1.0 那个病（回路断开）换了个位置复发。** 而且踩中的恰好是唯一有反馈入口的运行模式：

- `npm start`（`--once`）→ `if (telegram && !once)` 为假 → **根本不启动轮询器，没有输入通道**
- `npm run loop`（常驻）→ 启动轮询器，但 **100% 反馈被丢弃**

两条生产路径，反馈通过量都是零。

**为什么 67 个测试没抓到**：反测试每次都 `new MemoryStore(memoryDir)` 重新读盘，从未模拟"长驻对象 + 后续写入"这个真实拓扑。测试验证的是**函数组合的正确性**，不是**进程生命周期的正确性**。

**可证伪的反对意见**：有人会说"每轮跑完重启进程就没事了"。确实——但那要求 `--once` + 外部 cron，而 `--once` 模式压根不起轮询器。要同时满足"有轮询器"和"store 是新的"，当前代码无任何配置路径。反对不成立。

### V2：守卫的覆盖盲区

我把 `main()` 里的 `if (telegram && !once) { pollFeedback(` 改成 `if (false) { pollFeedback(`——**反馈接收端永不启动**。

```
Test Files  1 failed | 11 passed (12)
Tests  4 failed | 68 passed (72)     ← 红的 4 条全是我加的探针
```

**原有 67 个测试一条没红。** 可以把整个 Telegram 反馈接收端从进程里摘掉，交付报告依然能写"67 全绿"。

接线守卫守 8 个函数，**不守"谁启动这条链"**。而"链条被启动"恰恰是 v0.1.0 事故的定义性特征。

### V3：守卫本身是文本存在性检查，不是可达性检查

实测守卫正则 `(^|[^\w$])fn\s*\(` 的判定：

| 代码行 | 守卫判定 |
|---|---|
| `// 行注释里的调用 updateWeights(` | 判红 ✅ |
| `  * jsdoc 里的调用 updateWeights(` | 判红 ✅ |
| `/* 块注释里的调用 updateWeights( */` | **判绿 ❌** |
| `` const t = `模板字符串里 updateWeights(` `` | **判绿 ❌** |
| `if (false) updateWeights(a, b)` | **判绿 ❌** |
| `const dead = () => updateWeights(a, b)`（dead 无人调） | **判绿 ❌** |

### 残留的"绿灯但断开"路径清单

1. **链级**：`pollFeedback` / `main` / `runOnce` 均不在 GUARDED 列表，断掉任意一条都不红。
2. **进程级**：store 快照陈旧（V1），无任何测试覆盖长驻拓扑。
3. **配置级**：`process.argv[1].endsWith('index.js')` 决定 main 是否执行。用 `tsx src/index.ts` 跑 → 静默什么都不做，零报错、零输出。`npm start`/`loop` 都先 build，所以当前安全，但这是个无守卫的隐式契约。
4. **语义级**：一条反馈即使 `recorded` 了，`updateWeights` 的 α=0.2 步长也可能让权重变化小于浮点噪声——没有任何测试断言"变化量 > 阈值"，只断言 `toBeGreaterThan`。

## 二、刷新闸门的正确性

**结论：闸门在"追加"语义下正确，在"编辑"语义下有静默数据丢失。并发风险经实测证伪（我撤回原假设）。**

### 先说我错的那条（诚实记录）

我原本假设：长驻 store 的权重基线被冻结在进程启动时刻，导致学习无法复利。

**实测证伪。** `saveWeights()` 同时更新内存状态（`store.ts:79`），所以基线不冻结。30 次连续 👍：

```
[P2] 长驻模式 30 次👍后 rss-1 权重 = 0.962203847819051
[P2] --once 模式 30 次👍后 rss-1 权重 = 0.962203847819051
[P2] 差距 = 0.0000
```

两种模式完全一致。**这条假设撤回。** 真正的问题只在 archive 快照，不在权重。

### 真正的问题：计数不是版本令牌

`if (state.processedFeedback >= store.feedbackCount()) return current`

这个闸门隐含假设：feedback 只增不减、只追加不修改。而工作单自己把"手工编辑 feedback.json"列为**合法的反测试入口之一**（e2e 反测试第二条就是手工 `writeFileSync` 整个文件）。闸门假设与合法用法直接冲突。

**实测场景 A：修正一条反馈（条数不变）**

```
[P4] 手工改正前权重 = 0.4666666666666667
[P4] 改正后权重 = 0.4666666666666667   ← 未变，修正被静默吞掉
```

用户点错了，照说明手工把 👎 改成 👍 → 条数仍是 1 → 闸门关闭 → **这个修正永远不会生效**。

**场景 B：删除反馈（条数下降）**
`processedFeedback=10`，删掉 3 条误录 → `count=7` → `10 >= 7` → 闸门关闭，直到再攒够 4 条。**学习被冻结，且没有任何日志提示。**

**严重性评级：中。** 不致命（反馈主路径走 Telegram 追加，正常），但它是**静默**的——用户改正了数据，系统毫无反应，用户无法区分"改了没生效"和"权重本来就不该变"。对一个"让作者本人当第一个用户"的探针来说，静默失败是最伤的一种：它会污染人的直觉判断。

**并发：低风险。** 轮询器只在收到回调时写 `weights.json`；`runOnce` 侧因闸门关闭通常不写；`archive.json` 只有 `runOnce` 写。实测未构造出真实竞态。

### 修复建议

闸门改用**内容哈希**（对 feedback 数组排序后取 hash）或**文件 mtime**，不要用计数。计数在编辑语义下不单调，这是根因。

## 三、观测设计的盲区

**结论：区分不了。而且当前观测里"进化生效"的主指标是循环论证。**

### 盲区 1：`skippedSources` 根本没进持久化观测

commit `df17047` 的 message 写着"修 skippedSources 恒为空（**源挂掉不再被误读为池枯竭**）"。但实测：

```
[P5] observation 字段 = [at, candidates, pushed, candidateP50, candidateP90,
                         candidateTop1, pushedMean, saturationRate, weights, bySource]
[P5] 是否含 skippedSources = false
[P5] 是否含 collected/relevant/feedbackCount = [false, false, false]
```

`skippedSources` 只存在于 `RunResult.stats`，只被 `console.log` 打到终端，**不进 `observations.jsonl`**。两周后你分析 JSONL 时，那个用来区分"源挂了"和"池枯竭"的字段根本不在文件里。修复只做了一半，而这一半恰好是不落盘的那一半。

（补充：这也正好呼应第四条偏差裁决——见 §四。）

### 盲区 2：P50/Top1 记的是加权×新颖性分，不是原始分

`candidates = scored`，而 `scored` 已经过 `applyNovelty(applySourceWeight(raw, w), novel)`。实测：

```
[P6] 权重 0.5 时 P50 = 0.75   top1 = 0.75
[P6] 权重 1.0 时 P50 = 1.125  top1 = 1.125   ← 内容完全相同
```

**内容一个字没变，只把权重从 0.5 拉到 1.0，P50 涨了 50%。**

工作单写"top1 稳定 + candidateP50 上升 → 进化在起作用"。但这个指标**一部分在量你自己刚学到的权重**。权重上升 → P50 上升 → 判定"进化生效" → 权重继续上升。**闭环自证。**

要判定进化，必须看**原始分**上的 P50：内容质量真的变好了，还是只是你把好源的音量调大了？当前数据给不出这个区分。

### 盲区 3：学习越成功，饱和告警越会误报

`saturationRate` 判 `valueScore >= 0.99`，而加权分可以 >1（实测 1.125）。权重学到 1.0 时，任何原始分 ≥0.66 的条目加权后都 ≥0.99 → **saturationRate 冲到 1.0 → 触发"打分器又饱和了，其他观测全部不可信"的告警**。

健康进化会自己触发假警报。告警阈值必须改到**原始分**上算。

### 盲区 4：第三种失败模式完全无仪器覆盖

工单问的是"进化生效 vs 内容池枯竭/源挂掉"——**但实际上有三种模式，不是两种**：

1. 源挂了（fetch 抛异常 → `skippedSources`）
2. 池枯竭（fetch 成功，无新内容）
3. **源活着，但结构性零产出**（fetch 成功、有内容，但被 `isRelevant` 全滤掉）

实测归档（`memory/archive.json`，648 条）：

```
arxiv-cs-ai: 557    huggingface-blog: 74
github-new-llm-tools: 12    exa-llm-news: 5
v2ex-hot: 0    bili-llm: 0    hf-daily-papers: 0     ← 7 个源里 3 个零产出
```

`v2ex-hot` 返回中文话题，而 `domain.json` 的 17 个关键词**全是英文** → `isRelevant` 全滤掉 → fetch 成功（不算 skipped）→ 观测上显示为**健康的零产出**，与"源挂了"、"池枯竭"三者混为一谈。

### 未覆盖的混淆变量清单

源产出量 · 源语言与关键词匹配度 · 去重后的新内容率 · 聚类阈值变化 · 配额截断比例 · isNew 比例 · 归档裁剪（20000 上限触发后旧条目会被重新判为新） · 源查询窗口的时间漂移。**全部无仪器。**

## 四、8 条偏差的裁决

### a) 守卫正则放宽允许点号方法调用 → **允许**

工作单自带的实现代码就是 `store.recordFeedback(` 形式，原正则 `[^\w.$]` 会让它**永远无法转绿**。执行者是在修工作单的笔误，不是在修测试。放宽为 `[^\w$]` 保留了"有生产调用者"的本意。**判断：按本意修工作单。**

（但守卫本身太弱——见 §一 V3。放宽与否是次要问题，文本匹配范式本身才是主要问题。）

### b) `stats.pushed` 从簇数改为条数 → **允许，但改得不干净**

口径选择本身合理：工作单两条断言（`pushed=4` 与 `clusters=2`）确实自相矛盾，取条数更自然。

**但语义改了没传播**：`src/index.ts:209` 的日志还写着

```
`[run] 采集 ${...} → ... → 推送 ${result.stats.pushed} 簇`
```

现在是条数，不是簇数。**操作员看终端会得到一个错的数字。** 这是典型的"改了数据没改标签"，必须补。

### 最不该被允许的一条：**偏差 #5**

> 「Task 11 的 skippedSources 修复与守卫测试同批写入，缺一次独立红灯记录。」

执行者把它记为"已知偏差"，这**不能接受**。

而且**这不是无后果的形式问题**：缺红灯的那个 Task 11，改出来的 `skippedSources` 字段**根本没进持久化观测**（§三 盲区 1，实测确认）。这不是巧合，是缺红灯的直接后果——没有红灯倒逼你先问"改完之后，观测文件的字段列表会变成什么样"。

**要求：补做 Task 11 的独立红灯，并把 §三 盲区 1 一并修掉。**

## 五、sqrt 打分公式

**结论：是，任意性从参数搬到了函数形状。但真正的系统性偏倚不在形状，在输入长度。**

### 任意性确实只是搬家

`0.25 + 0.5*√(kw/8) + 0.25*√(sig/6)`——基础分 0.25、除数 8、除数 6、两个系数 0.5/0.25，**五个自由参数，零条校准数据**。旧公式至少还有"参数和阈值能对着调"的直观性；新公式把任意性藏进了函数形状，反而更难质疑。

### 真正的偏倚：长度

打分输入是 `title + body` **全文**。arXiv 摘要约 1000 字符，GitHub 条目约 100 字符。sqrt 压缩边际递减，但**不消除长度优势**——长文本的期望命中数就是更高。

实测归档 → **arxiv 557 : github 12 ≈ 46 : 1**。

### 阈值与公式的耦合（隐藏的硬门槛）

- 1 个关键词命中：`0.25 + 0.5*(1/√8) = 0.4268` → **< 0.45 阈值，直接被过滤**
- 2 个关键词命中：`0.25 + 0.5*(√2/√8) = 0.50` → 通过

**`scoreThreshold: 0.45` 的实际含义是"必须命中 ≥2 个不同关键词"。** 短文本源（GitHub 标题、V2EX 标题、B站标题）系统性死在门槛上，而这不是因为它们没价值。

### 两周结论的方向性偏倚

探针结论会系统性地说：**"arXiv / HF 博客这类长文源价值高，GitHub / V2EX / 视频类短文本源价值低"**。

但这是**文本长度的度量，不是信息价值的度量**。

放大到商业判定——"用户要不要一万个 bot"——结论会偏到：**要长文摘要型 bot**。而这可能纯粹是个长度伪影。更糟的是：这个偏倚会被反馈回路**固化**。用户 👍 那些（因长度）排在前面的条目 → 长文源权重上升 → 更靠前 → 更多 👍。**正反馈锁定。**

**建议**：LLM 打分接入前，打分输入应截断到固定长度（比如 title + body 前 300 字符），或按文本长度归一化命中数。否则两周数据从一开始就带着一个已知的、方向确定的偏差。

## 六、两周探针现在能开跑吗？

**不能。三条硬阻断，一条统计功效不足。**

### 硬阻断 1：跑了也是白跑，而且无法从事后数据里识别

V1 导致反馈 100% 丢弃。跑两周 = 记录两周的"零反馈"。结论会写成"用户不给反馈"，而真相是"系统接不住反馈"。**假阴性，且事后不可辨**——观测文件里没有任何字段能区分"用户没点"和"点了被扔了"。

### 硬阻断 2：无 Telegram key = 反馈回路没有输入通道

`--once` 模式不启轮询器；无 token 则 `telegram` 为 undefined。**探针测的就是反馈→进化回路，没有输入通道等于测空气。**

### 硬阻断 3：从来没有一条真实反馈流过系统

```
memory/ 下：archive.json ✅  observations.jsonl ✅
            weights.json ❌   feedback.json ❌
```

两轮真实运行、67 个测试——**零反馈**。所谓"红绿验证"验证的是**测试的有效性**，不是**系统的有效性**。这两者被混为一谈了。

### 统计功效不足（即使前三条全修好）

- 第 1 轮（冷启动）：647 条候选
- 第 2 轮（30 秒后）：**1 条**候选

稳态下每天新增候选是个位数到几十，且 **86% 来自 arXiv**（557/648）。每天推 6 条 × 14 天 ≈ 84 条推送。7 个源分下来，**每源约 12 次反馈**（乐观估计，实际因 arXiv 霸榜会更少）。

Beta(1,1) 后验 + α=0.2 步长下，12 条反馈最多把权重推动约 ±0.15。**两周数据无法区分"用户真的偏好某源"与"随机波动"。**

再加上无 LLM 打分——你测的是"启发式关键词打分 + 人工反馈"的回路，不是产品结论。**能得出的只有"回路通不通"，得不出"用户要不要一万个 bot"。**

## 七、无限定区：更要紧的话

### 1. 工单引用的数据，和盘上的 artifacts 对不上

工单 §二 引用第二轮：

```
工单：  "at":1788307612781, ... "bySource":{"github-new-llm-tools":1}
盘上：  "at":1788307618871, ... "bySource":{"exa-llm-news":1}
```

**时间戳和来源两个字段都对不上。**

工单自己写着"过程证据不是结果证据"——但它引用的这份**结果证据是手抄的，而且抄错了**。

这说明证据链在**第一步（转录）就已经有损**。建议：评审材料里的所有数据必须由脚本从 artifacts 直接生成，**禁止手抄**。这条比本轮任何一个代码 bug 都更值得写进流程。

### 2. 最该被问但没被问的问题：判定线在哪

这份工单问的全是"修对了吗"。但**两周探针的判定标准，从头到尾没有被写成一个可判定的命题**。

工单背景说：让作者本人当第一个用户跑两周，验证"千 bot 平台路线"。那请问：

- 两周后，**什么数据出现 = 要一万个 bot**？
- **什么数据出现 = 不要**？
- 中间地带怎么办？

**在没有这条判定线之前，所有 P0 修复都只是在让一个没有刻度的仪表变得更精密。** 精密到小数点后三位，然后不知道读出来意味着什么。

这是 P-1 级问题，比 P0 更靠前，且必须在开跑前定死——**事后定会自觉不自觉地向结果靠拢。**

### 3. `sources.json` 里有个冻结的日期窗口

```json
"url": "https://api.github.com/search/repositories?q=topic:llm+created:%3E2026-08-25&sort=stars&order=desc&per_page=15"
```

`created:>2026-08-25` 是**硬编码**的。探针跑两周期间窗口起点不动，按 star 降序取 top-15 → 返回的几乎总是同一批 repo → **这个源在探针期间基本不产生新信号，但权重照常学它**。

要么改成相对日期（`created:>{7天前}`），要么在观测里显式标注该源的新内容率。

### 4. 关于"AI 修 AI 写的工单"

工单 §四 已经指出这个链条的共同盲区：**对工程完备度的共识系统性高于对真实用户价值的关注。**

本次交付是这个盲区的教科书级样本：

- 14 个 Task、67 个测试、红灯存档、红绿验证、快照证据——**工程完备度接近满分**
- 生产环境反馈通过量 = 0，**零条真实反馈流过系统**——**用户价值验证 = 0**

而且交付报告通篇没有一处问："所以，真的有一滴反馈流过去了吗？"

**建议**：以后每个 P0 验收，第一条检查项固定为——**"从真实入口走一遍，把落盘的 artifacts 贴出来"**。不是贴测试输出，是贴 `feedback.json` 和 `weights.json` 的真实内容。如果这两个文件不存在，验收直接终止。
