工作单把障碍描述为「尚未启用：Telegram 反馈按钮（**缺 token**）」，这会让人以为填上 token 就能跑。**填上也跑不了，缺的是整个接收端。** README 的「已知边界」诚实写了这点，工作单没写——这构成对评审者的信息不对称。

## 一、定向问题逐条答复

### 问题 1：探针逻辑本身——一个 bot + 一个用户 + 两周，能否为「千 bot 需求」提供有效证据？

**结论：反对（作为验证手段）。它能证伪，不能证实。而工作单把它当成能证实的。**

理由。这个推论跳了三层：

| 层 | 命题 | 探针能否回答 |
|---|---|---|
| L1 | 我会持续用我自己设计的领域 bot | 能（弱） |
| L2 | 别人会用别人定制的领域 bot | **不能** |
| L3 | 存在一万个有商业价值的领域 bot，且有人付费 | **完全不能** |

L1→L2 的跳跃就是设计者污染，工作单自己承认了。但真正致命的是 **L2→L3，工作单压根没提**：「千 bot 工厂」的商业赌注是**数量级假设**——有足够多值得做、且愿意付费的领域。一个 ai-llm 领域的、我自己做的、零边际成本的 bot，**对这个数量级假设的信息量是零**。

一个信息追踪 bot 跑通了，最多说明「LLM 从业者需要信息追踪」，这是 Google Scholar / arXiv 推送早就解决的需求。它不说明第 2 个、第 1000 个领域在哪儿。

**通过线的三个具体问题：**

- **👍率 ≥ 30% 无对照组，这个数字什么都说明不了。** 推送的是从 960 条里挑出的 top-6，且 72% 来自 arXiv cs.AI（实测）。对 AI 从业者来说，arXiv 新论文标题的基线 👍 率可能本来就有 40%。过线不能证明「推送有价值」，只能证明「arXiv 论文标题对 AI 从业者不是噪音」——这个结论不用花两周也能知道。**应该定相对基线，不是绝对值**：比如「bot 精选 6 条的 👍 率 ≥ 直接读 arXiv RSS 前 6 条的 👍 率」。没有对照组的阈值是自欺。
- **查看 ≥ 10 次会自动通过。** 两周 10 次 = 每天 0.7 次。作者知道自己造了这个东西，novelty effect 就够撑过这条线。**这条线必须改成「第 2 周的查看次数 ≥ 第 1 周」**——测的是留存，不是新鲜感。新鲜感人人有，留存才是需求。
- **「第 3 轮起噪音可感知下降」在数学上不可能**，见问题 2 的节奏错配——按当前配置，噪音只会上升。这条线设了也测不到。

**可证伪的反对意见：** 如果你的目标本来就不是验证 L3，而是「给自己造个能用两周的工具，顺便看看反应」，那这个设计完全合理——但那就别叫「假门测试」，也别用它去给千 bot 路线争取投入。**把工具当探针用，最危险的不是它失败，是它成功了。**

### 问题 2：自进化的技术路线——天花板在哪？Beta(1,1) + α=0.2 稳健吗？

**结论：数学部分没问题，但被两件事架空——(a) 代码没接线，(b) 反馈信号根本不够喂它。**

先说好的：`sourceValue` 用 Beta(1,1) 后验均值是对的，α=0.2 的指数移动平均在小样本下也稳。**这部分设计我同意，不用改。**

问题在信号量。做个算术：

- 每轮推 6 条，每天按 README 的 `DOMAIN_BOT_POLL_MS=3600000`（1 小时）跑 24 轮 → 理论 144 次反馈机会/天。
- 实际人不会每小时点 6 次按钮。**现实估算：每天 2-4 次反馈**，两周 = 28-56 次。
- 摊到 7 个源 → **每源两周平均 4-8 次反馈**。

Beta(1,1) 在 4-8 次样本下的后验均值，标准差约 0.12-0.15。而源权重的可辨识差异……你自己看 `applySourceWeight`：`valueScore * (0.5 + weight)`。权重从 0.3 涨到 0.7，有效分只从 ×0.8 变到 ×1.2。**权重的调节幅度（±20%）跟权重的估计误差（±0.13 → ±13% 的相对调节误差）在同一量级。**

**直白说：两周的信号量，只够把权重从噪音里勉强捞出来，不够让它产生可感知的排序变化。** 「第 3 轮起噪音可感知下降」这个通过线，在样本量上不成立——第 3 轮时每源大约只有 1 次反馈。

**更要紧的：反馈归因到「源」是错的。** `recordFeedback` 记录 `{itemId, source, signal}`，但 `feedbackBySource()` 只按 source 聚合（`src/memory/store.ts:117`）。你推送的是**从 960 条里精选的 top-6**——对精选内容的 👎，不代表这个源差，只代表这一条不对胃口。用一个已经过筛的样本的反馈去给未筛的整体打分，是**采样偏差**。

后果是：你永远学不到「哪一类内容好」，只能学到「这个源最近运气好不好」。而「哪一类内容好」才是千 bot 工厂真正需要的能力。

**可证伪的反对意见：** 如果两周后你把 `pollMs` 调大、源减到 3 个、每轮推 10 条，信号量能翻 3-4 倍，权重才可能收敛出可辨识的差异。**路线不用改，参数要改。** 也可以退一步：不要源级权重，改成**条目特征权重**（关键词/信号词/内容类型），因为条目特征的样本量是推送条数（几十），不是源数（7）——同样的数据量，学习效率高一个量级。

### 问题 3：价值打分冷启动——启发式打分器还有什么更大的坑？

**结论：有条件同意过渡方案，但你们盯着的地方不对。真正的坑在 LLM 侧，而且会直接炸。**

**已验证的坑（我跑了实际验证）：关键词子串误伤，相关性过滤形同虚设。**

`filterRelevant` 用的是 `hay.includes(keyword)`（`src/refinery/filter.ts:7`），纯子串匹配。关键词表里有 `rag`、`llm` 这类 3 字母词。实测：

```
"storage"     -> 命中 "rag"      ← s-t-o-r-a-g-e
"paragraph"   -> 命中 "rag"
"average"     -> 命中 "rag"
```

后果是双重的：
1. **无关内容能通过相关性过滤**——一条讲 storage 的文章因为命中 "rag" 就进了候选池。
2. **长文本系统性得高分**——`kwHits` 是计数，没有按长度归一化。arXiv 摘要 300 词 vs Exa highlights 20 词，前者命中数天然高一个量级。**这就是工作单说的"偏袒 arXiv 式长摘要"的真实机理，配额只是在事后砍掉超额部分，没有修正打分本身。**

最讽刺的一点：**Exa 是语义搜索，返回的内容已经被上游语义筛选过了；arXiv RSS 是未筛选的全量。你的打分器在惩罚上游已经做好的筛选工作，奖励未筛选的长文本。** 实测 exa 只贡献了 5/29 条推送，而它是权重最高（0.6）的源之一。

**建议的最小修复（一行）：** 关键词匹配加词边界，且 `kwHits` 按文本长度归一化（`hits / sqrt(token_count)`）。这比每源配额更本质。

**但真正的坑在 LLM 侧，工作单问错了方向。看 `LlmScorer.score`（`src/refinery/scorer.ts:47-83`）：**

- **D1 · 不分批，960 条塞进一个 prompt。** `items.map((it,i) => ...).join('\n')`，每条 body 截 600 字 → 单次请求约 50 万 token。必然超限/超时/截断。
- **D2 · 失败时降级到常数 0.5，比启发式还差。** 第 73 行：`items.map(() => ({valueScore: 0.5, ...}))`。一旦 LLM 返回被截断（几乎必然），**所有条目同分 → 排序退化成源权重排序 → 实际是随机推送**。而启发式至少还能给出一个有区分度的排序。**正确做法是 LLM 失败时降级回 `HeuristicScorer`，不是降级回常数。**
- **D3 · 没接 LLM 时没人发现，接了才发现，而那时你已经跑了几天数据了。** 这个坑的特点是：不接 LLM 永远看不见，一接就炸，且炸的方式是"静默变差"（推送照常，质量崩了，你以为是自己兴趣变了）。

**可证伪的反对意见：** 启发式打分器的坑（长摘要偏袒）是**渐进的、可忍受的**；LLM 打分器的坑是**断崖式的、会污染你两周数据的**。如果只能修一处，修 LLM 侧：分批（每批 20 条）+ 失败降级到启发式 + 单轮 token 预算上限。

### 问题 4：渠道策略——排除需登录通道，对信息质量的伤害多大？

**结论：同意这个取舍，但你们高估了当前渠道的多样性——实际只有 3 个源在干活。**

先看实测。`memory/archive.json` 29 条推送的来源分布：

```
arxiv-cs-ai            21  (72%)
exa-llm-news            5  (17%)
huggingface-blog        2  ( 7%)
github-new-llm-tools    1  ( 3%)
v2ex-hot                0
bili-llm                0
hf-daily-papers         0
```

**7 个源，3 个从未产出过任何推送。** 逐个查原因：

| 源 | 状态 | 原因 |
|---|---|---|
| `hf-daily-papers` (jina) | **死** | `r.jina.ai` 无 key → 401 → throw → 被 catch 静默吞掉 |
| `v2ex-hot` | **结构性死** | 抓的是 V2EX **全站热门**，跟 LLM 领域无关 → 命中不了关键词 → 全被 `filterRelevant` 淘汰 |
| `bili-llm` | **结构性死** | 抓的是**中文**标题（`大模型 最新`），而 `domain.json` 的 17 个关键词**全是英文** → 中文内容永远命中 0 个关键词 |

后两个不是 bug，是**配置组合错误**：源的语言/领域，和关键词表的语言/领域对不上。**这个源从接上的那一刻起产出就是 0，而且因为 `skippedSources` 永远是空数组（见下条），你从日志里完全看不出来。**

所以「多渠道」实际是「arXiv + 一点点 Exa」。配额机制让 arXiv 从 72% 降到 50%（实测 18:35 那轮是 arXiv 3 + HF 2 + GitHub 1），但池子里本来就没别的货。

**关于排除 Twitter/Reddit/小红书：同意。** 无人值守 + 登录态 = 封号，这个风险不对称（收益是边际信息，损失是账号资产）。不值得。

**两全方案（如果真想要 Twitter 的内容，按性价比排序）：**

- **A（推荐）· Nitter / RSS 镜像。** 无需登录，有公开实例。缺点是实例不稳定，需要备用列表。
- **B · Reddit 官方 JSON API**。`reddit.com/r/X/new.json` 无需登录（限流宽松），加 UA 即可。Reddit 的技术讨论密度远高于 V2EX，性价比高。
- **C · 不接。** 先把现有的 3 个死源救活——**修好 2 个已接但产出为 0 的源，比新接 2 个源便宜得多**。

**可证伪的反对意见：** 我判断「排除登录态通道」对**你这个领域**（ai-llm）伤害不大——LLM 领域的一手信息本来就在 arXiv/HF/GitHub/Twitter，而 Twitter 有 Nitter 替代。但如果千 bot 工厂瞄准的领域是**消费、时尚、本地生活**，那 Twitter/小红书/Instagram 就是主渠道，免登录方案覆盖不到。**这个取舍的结论不能跨领域外推**——这恰好也打击了「可复制性」声明（问题 6）。

### 问题 5：防自我固化——还有什么机制层面的固化风险？

**结论：有，而且是最要紧的一个。删 ε-greedy 时把探索机制整个删掉了——而它本来该在另一个位置。**

先复盘你们做对的部分：ε-greedy 按轮跳源确实有害（低权重源大部分轮次静默，反而拿不到反馈），删掉是对的。**但删掉的同时没有在任何地方补回探索，这是把"这个位置不该探索"误读成了"不需要探索"。**

关键在于分清两个位置：

| 位置 | 每轮规模 | 探索的作用 |
|---|---|---|
| **抓取位** | 1670 条 | **无效**。抓了不推，不会产生反馈信号 |
| **推送位** | **6 条** | **唯一有效**。用户的 👍/👎 只发生在被推送的内容上 |

ε-greedy 装在抓取位 → 无效（你们实测到了）。但正确的结论不是"不要探索"，而是**"把探索从抓取位移到推送位"**。全量抓取 1670 条不产生任何探索价值——用户只看得见那 6 条。

**固化死循环的完整链条（这是我要给的最高优先级风险）：**

```
源权重下降
  → 有效分 = valueScore × (0.5 + weight) 变小
  → 但注意：过滤阈值 0.225 是在乘完权重之后才判的
    （src/index.ts:72：scored.filter(s => s.valueScore >= threshold*0.5)）
  → 权重低的源，条目被「淘汰」而不是「降权」
  → 该源不再出现在推送里
  → 拿不到任何反馈
  → 权重永远锁死在低位
```

**"降权"和"处死"是两回事，而当前代码做的是后者。** 一旦某个源被 👎 几次，它就再也不会出现在你面前——不是因为它真的差，是因为它失去了被证明的机会。这正是你们想防的"自我固化"，而它此刻就在代码里。

**具体触发点算给你看：** `HeuristicScorer` 最低分 0.3（0 命中，`scorer.ts:28`）。权重降到 0 时，有效分 = 0.3 × 0.5 = **0.15 < 0.225 → 淘汰**。也就是说，**一个权重被打到底的源，连"命中 0 个关键词"的资格都没有了**。

**修复建议（三选一，按推荐度）：**

- **A（推荐）· 把过滤和排序解耦。** 过滤用**原始价值分**（不过权重），排序才用加权分。权重只决定「排第几」，不决定「能不能出现」。这是最小改动，一行。
- **B · 推送位保底配额。** 每轮 6 个位置里，固定留 1-2 个给"当前权重最低的源的最优条目"。这才是 ε-greedy 的正确位置。
- **C · 权重下限锁。** 权重 clamp 到 `[0.2, 0.8]`，永不归零。

另外两个较小但真实的固化风险：

- **反馈只有 up/down，没有「没点」。** 推送了但用户没反应（大概率是没看/没兴趣），这个信号完全丢失。`feedback.json` 里只有被点过的记录。建议每轮结束时，对**上一轮推送中未获反馈的条目**补记一条弱负信号（或至少记录「已推送未反馈」计数）。
- **`memory/archive.json` 只记录被推送的条目**（`src/index.ts:95` 的 `recordItems(scored)`）。未推送的 ~954 条相关条目不入库 → 下轮重新打分（LLM 接入后是**重复烧钱**）→ 而且换个标题就能重复推。

### 问题 6：可复制性——「加一个领域 = 改一份 config」，离这个声明还差什么？

**结论：差得远。当前实现离这个声明至少差 4 处硬编码，而且最要紧的一处是"语言假设"，不是代码。**

**硬伤 1 · 语言假设（最要紧）。** 打分器和过滤器假设「内容语言 = 关键词语言」。你要加一个中文领域（比如「国内房地产政策」），光改 `domain.json` 的关键词没用——`bili`/`v2ex` 这类中文源已经在那里了，而当前 `ai-llm` 领域的中文源产出是 0。**反过来说，你加了中文关键词后，arXiv 的英文摘要又会被误伤。** 需要的是 per-source 的语言标注 + 关键词表分语言，这是 config schema 的改动，不是"改关键词"。

**硬伤 2 · GitHub 源 URL 里硬编码了日期。**
```
.../search/repositories?q=topic:llm+created:>2026-08-25&sort=stars&per_page=15
```
`created:>2026-08-25` 是写死的。两周后它查的是"2026-08-25 之后创建的 repo 里 star 最高的 15 个"——**这是存量 top15，不是增量**。它会逐渐退化成一份静态名单（永远是新注册的 star 最高那几个，不再变化）。config 需要一个模板变量：`created:>{{since_days:7}}`。

**硬伤 3 · 信号词表在代码里，不在 config 里。** `HeuristicScorer.signals`（`scorer.ts:21`）硬编码了 `['release','benchmark','sota','beat',...]`。这套信号词是**为 ai-llm 领域挑的**（SOTA、benchmark、inference）。换到「房地产政策」领域，这些词全都失效，而换领域的人要改代码才能换——**直接违反"无需改代码"**。

**硬伤 4 · 源类型是封闭枚举。** `collectSource`（`src/index.ts:133`）是硬编码 switch。加一个新渠道类型（比如 Reddit JSON）必须改 `src/`。这在一定程度可接受（适配器本来就是代码），但意味着"改 config"只能覆盖已有类型的排列组合。

**最小达标清单（声明可复制性之前必须做完）：**

1. `signals` 移到 `domain.json`
2. GitHub/搜索类源支持日期模板变量
3. 关键词表支持 per-source 语言分组（或至少 `lang: zh|en` 标注）
4. **至少在一个非 ai-llm 领域真跑通一次**——这是唯一的证明方式

第 4 条最重要。在第二个领域跑通之前，「无数个 bot 就可以跑通」是一句**未经检验的信念**，不是结论。**而按问题 4 的分析，不同领域的最优渠道组合根本不同（ai-llm 靠 arXiv，消费领域靠小红书），所以"换个 config 就能复制"这个前提本身可能是错的。**

**可证伪的反对意见：** 如果千 bot 工厂的目标领域本来就高度同质（全是"AI/技术类"），那 config-only 是够的。但这跟"一千个 bot"的数量级假设直接矛盾——一千个同质的技术 bot ≠ 千 bot 工厂。**这两个信念至少有一个是错的，值得现在就想清楚。**

### 问题 7：两周后的决策框架——什么结果该加注 / 改设计重跑 / 放弃？

**结论：给出判据，但先警告一句——按当前配置跑出来的数据，无论什么结果都不能用于决策。**

原因见「零」：进化环没接线，节奏错配（见无限定区 U1），通过线无对照组。当前配置下：
- 如果结果显示"有效" → 无法区分是"bot 真的有用"还是"arXiv 标题本来就不讨厌"
- 如果结果显示"无效" → 无法区分是"需求不成立"还是"代码没接线 / 节奏错了"

**所以第一件事不是定判据，是先让数据可解释。** 修完 P0（见下）再跑，否则两周白费。

**修完之后，用这个判据（三选一，按顺序判）：**

| 判据 | 加注 | 改设计重跑 | 放弃 |
|---|---|---|---|
| **第 2 周查看次数 vs 第 1 周** | ≥ 80%（留存住了） | 40%~80%（有兴趣但没粘住） | < 40%（新鲜感过了就不看） |
| **👍 率 vs 手工基线**\* | 显著高于基线 | 与基线持平 | 低于基线 |
| **未推送条目里能找到更好的吗**\*\* | 没有（bot 挑得比我好） | 偶尔有 | 经常有（bot 漏掉了好东西） |
| **第 2 周 👍 率 vs 第 1 周** | 上升（进化生效） | 持平 | 下降（可能是质量衰减，见 U1） |
| **你会主动加第二个领域吗** | 会，且马上 | 想过，不急 | 不会 |

\* **手工基线**：连续 3 天，每天从 arXiv cs.AI RSS 手工挑 6 条，记录自己的 👍 率。**没有这个数字，👍率 ≥30% 无法解释。**
\*\* 每周抽 1 轮，人工扫一遍被过滤/未推送的条目，看 bot 是否漏掉了你会 👍 的内容。**这是唯一能测出"打分器不行"的方法，也直接回答问题 3。**

**判据的优先级：第 2 周留存 > 第 2 周 👍 率 > 绝对 👍 率 > 绝对查看次数。** 你们当前的表把权重放反了——最弱的两个指标（绝对查看次数、绝对👍率）被当成了主要判据，最强的两个（留存、对照）根本没设。

## 二、无限定问题区

### U1 · 节奏错配：这是最隐蔽、也最可能毁掉两周数据的设计错误

`DOMAIN_BOT_POLL_MS` 默认 **3600000 = 每小时一轮**（`src/index.ts:166`），README 推荐 `npm run loop` 常驻。但：

- 采集源的更新频率是**每天**（arXiv 每日更新、HF blog 每周几篇、GitHub 每日 top15）
- 管线的运行频率是**每小时**
- 单轮采集 ~1670 条，推送 6 条 → **1670 / 6 ≈ 278 轮耗尽新内容**

后果：第 1 轮推的是 1670 条里最好的 6 条；第 10 轮推的是第 60 名左右的条目；**第 278 轮（约 11.6 天）开始推重复内容**。质量在整个两周里**单调衰减**，而**没有任何指标能让你看见这个衰减**——你只会感觉"最近推送变水了"，然后归因为"进化没学好"或"我自己兴趣变了"。

**这直接伪造了问题 1 的第三条通过线**：「第 3 轮起噪音可感知下降」。按当前配置，第 3 轮的噪音是**上升**的，因为好东西前两轮就推完了。

**修复：改成每天 1-2 轮（`DOMAIN_BOT_POLL_MS=86400000`），并在每轮输出里打印"本轮 top1 分数"这个时间序列。** 没有这个序列，你无法区分"进化在起作用"和"内容池在枯竭"。

### U2 · 测试绿给了虚假的完成度信号

`tests/e2e.test.ts:69-84` 有个用例叫「反馈回路：👍 后源权重上升，进化可复算」。它做了什么：手动 `new MemoryStore` → 手动 `store.recordFeedback(...)` → 手动 `updateWeights(sources, store.feedbackBySource())` → 断言权重上升。

**这个测试是绿的，但它验证的是"三个函数单独可用"，不是"进化环已接通"。** 生产代码里这三个步骤一个都不会自动发生。35/35 全绿，恰恰是让人（和 LLM 评审者）误判"进化环已通"的最大诱因。

**建议：加一条反测试。** 断言 `runOnce` 连续跑 10 轮 + 注入 10 条反馈后，`config/sources.json` 的权重**发生了变化**。这条测试现在是红的，它应该红着——它红了才说明你知道系统真实状态。

### U3 · 监控盲区：`skippedSources` 永远是空数组

`src/index.ts:45` 声明了 `const skipped: SourceConfig[] = []`，但 catch 块（`:54-56`）只 `console.error`，**从不 push**。所以 `stats.skippedSources` 恒为空。

后果：源静默失败你看不见。`hf-daily-papers`（jina）从接上就 401，三周后你也不会知道——你只会看到"采集量从 1670 掉到 1400"，然后以为"今天 arXiv 更新少"。

**修复（两行）：** catch 里 `skipped.push(source)`，并在每轮结束时打印源级产出表（源 id / 采集条数 / 通过过滤数 / 入推送数）。**这张表应该是每轮的标准输出，不是调试时才加。**

### U4 · `isNovel` 的 O(n×m) 和它的无效性

两件事：

1. **无效**：29 条归档 100% 标 🆕，jaccard 阈值 0.7 太严，实际从未触发「旧闻」。这个标记现在是纯装饰。
2. **会变慢**：`isNovel` 对每条候选扫全表（`store.ts:61-71`）。归档上限 2000 条 × 每轮 960 条候选 = **每轮约 190 万次 jaccard**。虽然 `tokenCache` 缓存了归档侧，但每次 `runOnce` 都 `new MemoryStore`（`index.ts:42`）重建缓存。当前 29 条无所谓，涨到 2000 条会明显变慢。

**建议**：要么让 `isNew` 真正参与排序（同分时优先推新），要么删掉这个功能减少自欺。**一个 100% 恒真的标记比没有标记更糟——它让人以为有个机制在工作。**

### U5 · 「为什么值得看」这个位置被浪费了

实测推送里每条的推荐理由长这样：

```
- 为什么值得看：关键词命中 5，信号词命中 1
- 为什么值得看：关键词命中 4，信号词命中 2
```

**这是推送里最有说服力的位置，被填了一句对用户毫无信息量的机械统计。** 用户看到 6 次"关键词命中 N"之后，这个字段就是噪音，甚至会**降低 👍 率**——因为它暗示"推荐理由是凑关键词"，动摇信任。

**最小改进**：输出命中的具体关键词，或者「与你第 N 轮看过的 X 相关」。LLM 接入后这里应该输出一句话理由。**这个改动成本极低，对 👍 率的影响可能比调权重还大**——因为它直接影响用户判断"要不要点开"。

### U6 · 你们没问但最该问的：探针的「退出条件」是什么

工作单详细定义了"什么算通过"，但没定义**"什么情况下我该停下来"**。这在做假门测试时是危险的——没有退出条件的实验，会在结果模糊时被无限延长，直到某天出现一个好数据然后宣布成功。

**建议在开跑前写死并存档（不可事后修改）：**

1. 两周到期，无论数据如何，**先停 3 天不跑**。3 天后如果发现自己**想主动把它开回来** —— 这是比任何 👍 率都强的需求信号。如果 3 天都没想起来，那就是答案。
2. 如果两周内出现"连续 3 轮没有任何反馈" —— 立即停。不是改参数继续跑，是停。这表示用户（你）已经不看了，继续跑只是攒噪音数据。
3. 数据解释权在开跑前锁定：本报告第七节的判据，写入 `docs/`，两周后不得修改。

**第 1 条是我认为整个探针里最有价值的设计**——它测的是「戒断反应」，而不是「使用量」。使用量可以靠新鲜感撑两周，戒断反应撑不了。

## 三、总判断

### **改设计后值得。**

不是"值得"（当前配置跑两周会得到一堆无法解释的数据），也不是"不值得"（探针本身的方向是对的，且成本极低）。

**必须改的三件事（P0，否则两周数据不可解释）：**

| # | 改什么 | 为什么 | 成本 |
|---|---|---|---|
| **P0-1** | **把进化环接上**：加 Telegram getUpdates 轮询（20 行）或一个 webhook 端点；轮次开始时调 `updateWeights` 并把结果写回 `config/sources.json` | 否则"自进化"这条命题两周内不可能被验证 | 半天 |
| **P0-2** | **节奏改每天 1-2 轮**，并在每轮输出 top1 分数时间序列 | 否则质量单调衰减污染所有信号 | 5 分钟 |
| **P0-3** | **推送位恢复探索**：每轮 6 个位置固定留 1 个给最低权重源的最优条目；同时把过滤阈值改为作用在**原始分**上（不过权重） | 否则源权重一旦下降就永久锁死 | 1 小时 |

**应该改的（P1，影响数据质量但不致命）：**

- P1-1 · 关键词匹配加词边界（修 "rag" 误伤）+ `kwHits` 按文本长度归一化
- P1-2 · 修 `skippedSources`（catch 里 push）+ 每轮打印源级产出表
- P1-3 · 建立手工基线（连续 3 天手工挑 6 条，记录 👍 率）
- P1-4 · LLM 打分器分批（20 条/批）+ 失败降级到启发式（不是降级到常数 0.5）
- P1-5 · 把死掉的 2 个源救活（v2ex 换成 LLM 相关节点、bili 加中文关键词）或直接删掉——**留着 3 个产出为 0 的源会让你误以为有 7 个渠道**

**不用改的：**

- Beta(1,1) + α=0.2 的权重更新数学 —— 设计对，保留
- 免登录渠道策略 —— 同意，别接登录态通道
- 每源配额 —— 作为兜底保留（实测有效：arXiv 从 100% 降到 50%）
- JSON 文件记忆库 —— 这个量级下正确选择，别上数据库

**最后一句（这是我最想说的）：**

这个探针最大的风险不是失败，是**以错误的方式成功**。你会用它两周，看到 6 条 arXiv 标题，觉得"还挺有用"，点几次 👍，然后得出"需求 50 成立"的结论。但那个结论真正的支撑是「arXiv 论文标题对 AI 从业者不是噪音」——**这件事你花两周之前就知道**。

所以请在开跑前把这句话写进 `docs/` 并存档：

> **本探针只能证伪，不能证实。** 如果我（老张）两周后不看了，可以放弃千 bot 路线；如果我还看，只能说明"我需要这个工具"，**不构成"用户需要一万个 AI bot"的证据**。

写下来，两周后才不会改。
