# 整改计划：关键词召回加宽（recall widening）

> 起因：老张 2026-09-05 批评「**用关键词搜索内容会限制信息渠道**」。触发观察：白天滚动采集窗口各源「最新列表」恰好无关键词命中 → `afterRelevance=0` → 整轮空转（第二/三轮批产实验，deepthought 40→1→0、newsline 16→0→0，其中第二轮的 1/0 是防重放，第三轮的 0/0 是关键词全灭）。
> 状态：**计划**（非裁决、非工单）。实施需老张拍板。
> 编制：小智（ZCode 代理总管）2026-09-05。

---

## 一、问题定性（机制证据）

当前候选入选链（`src/gates/index.ts:60-90`）：

```
persona 前置（时间窗）→ 黑名单 → 相关性积分闸门 → 规范 URL 去重 → 事件聚合 → 终审 → 发布
```

**相关性积分闸门（`src/gates/relevance.ts:64`）是硬入选条件**：`points >= minPoints(3)` 才继续，否则 drop（`relevance:belowMinPoints`）。词表 = core 51 词（+3）+ ecosystem 20 词（+1）+ generic 7 词（0）。**这 78 个词就是全管线的可见性边界**：

1. **词表外内容结构性不可见**：AI 合规/治理、模型经济学、芯片与硬件、开源生态、上下文工程、体现论/安全性（alignment/safety）等交叉领域——只要标题/正文不命中 78 词积分凑不满 3，无论多有价值都无法进入候选。这不是「宁可错杀」的质量判断，是「词表没写就永远不见」的召回缺陷。
2. **同一问题存在于两层**（老张「关键词搜索」表述的完整含义）：
   - **源查询层**：`exa-llm-news`/`exa-agent-releases`/`github-*`/`yt-llm` 适配器本身用关键词查询串拉取（`config/sources.json` 的 `query` 字段）——查询串限定可见集合，闸门层再按 78 词筛一轮，双回收窄。
   - **闸门层**：relevance 积分 <3 硬淘汰（本文档重点）。
3. **时空稀疏**：不同时段各源「最新列表」的关键词命中密度天然不同——凌晨吃隔夜积累（deepthought 915 条、40 过闸），白天逐小时增量恰好无命中 → 0 候选。整改前「白天空转」是结构必然，不是运气。
4. **词表漂移负担**：AI 术语半年一变，人工维护 78 词必然滞后。词表是「当时的认知快照」，不是「相关」的可信定义。

**必须澄清的语义**：「宁缺毋滥」正确语义是**质量门槛**（不知道好坏时宁可不发），不是**召回限制**（词表外一律不见）。整改不放松质量，只放宽可见性。

## 二、设计原则

1. **关键词是召回信号，不是入选标准**：相关性判定的权威从词表交回内容本身。
2. **双通道召回**：快通道（关键词高置信命中，现状保留、开销低）+ **宽通道**（非黑名单、非空、长度达标的一切条目，进轻量筛选，不设关键词门槛）。
3. **质量与召回解耦**：宽通道条目必须走同一条终审链（十条客观断言 + 事件聚合），禁止任何绕过质量的捷径——否则就是把「宁缺毋滥」换成「什么都发」。
4. **LLM 判定只做召回/预筛，不做终审**：保持 DB-04 §六.4 裁决「LLM 分数不做闸门、合格与否由十条断言定」——宽通道里 LLM 的角色是「是不是相关内容、值不值得进池」的二元判定，不是质量打分。
5. **成本受控**：宽通道设每 persona 每轮上限（建议 ≤20 条进 LLM 判定），不把全量采集都推给 LLM。
6. **不引入新影子工序**：宽通道全部落仓内可测管线（wiring 守卫扩到新路径，测试钉死）。

## 三、方案分层

### Phase 1：止血（低风险，词表治理 + 查询串加宽）

1. **词表增补**：core/ecosystem 补当前热门漏网词（草稿示意，实施前再定稿）：
   - core 候选：`alignment`、`safety`、`context window`、`context engineering`、`agents`、`agentic`、`mcp`、`model context protocol`、`distillation`、`蒸馏`、`量化`、`quantization`、`speculative decoding`、`rlaif`、`jailbreak`、`gradient`、`scaling law`、`multimodal`、`多模态`、`loRA/fine-tuning 变体`。
   - ecosystem 候选：`compliance`、`governance`、`copyright`、`energy consumption`、`inference cost`、`open weights`、`前沿`、`发布`。
   - ⚠️ generic 层不加词（0 分词不贡献入选，加了只稀释计分占比）。
2. **源查询层加宽**：exa/github/ytsearch 的 `query` 从「窄查询」扩为「域宽查询」（如 `AI models, agents, inference, research, ecosystem, safety, hardware, economics`），让单轮候选上界不取决于单个查询串的覆盖；质量仍由闸门后段把守。
3. **验证**：三个白天小时段试跑，观察 `afterRelevance` 是否仍恒 0；若还恒 0 → 说明止血不够，直接进 Phase 2。

> 诚实说明：Phase 1 只是把词表边界往前推了一格，**没有消灭「词表=边界」的结构**——为什么不做大词表：词表永远追不上术语迁移，维护成本随规模上升且看似「够用」反而麻痹。

### Phase 2：结构性反转（核心整改，建议进入）

1. **relevance 从硬闸门降为快通道标记**：`gates/index.ts` 的 4 步流水线改为——
   - relevance 通过的条目 → 快通道（现状语义，`relevance:passed` 标记）；
   - 未通过但满足「非黑名单 + 标题/正文非空 + 长度 ≥ minTitleChars + 语言可读」的条目 → **宽通道待定池**；
   - 黑名单命中依旧一票否决（宽通道不得绕过）。
2. **宽通道筛选（新模块，如 `src/gates/recall.ts`）**：
   - 启发式预筛（标题去噪/纯列表/重复句式——复用黑名单与 `gatekeeper` 的断言思路，规则化、可测试）；
   - 预筛通过的、按每轮上限取前 N 条，交 **reviewer 二元判定**（复用已 calibrate 通过的 DeepSeek 链，新 prompt「这篇值不值得进 AI 信息流」+ 输出 `{include: boolean, category, reason}`，**不做打分**）——单独小标集校准该判定口径（沿用 calibration 机制，若一致率不足则退回启发式只筛不发）；
   - 判定 include 的条目并入现有快通道后续（事件聚合 → 十条断言 → 发布），**终审不变**。
3. **persona 配置**：`recall: { enabled: boolean, maxPerRound: 20, llmGate: 'reviewer' | 'off' }`；默认 `llmGate:'reviewer'` 待定（见拍板点 2）。
4. **可观测**：看板新增宽通道漏斗（`collected → recallPool → llmInclude → afterGates`），与现有漏斗并列，不得静默吃掉任何一跳。

### Phase 3：调度与候选池化（治「高峰依赖」的残余，可缓）

1. **多时段 plist**：03:00/12:00/19:00 三时段（对齐北美/欧洲/亚洲发布节奏），每轮独立——简单先行。
2. **候选池化**（可选后续）：跨轮累积低产出候选（staging 快照），发布前合并多轮池再遴选——改动较大（storage 契约 + 幂等），Phase 2 落地且白天仍有空窗再议。

## 四、兼容性核对（整改不得破坏的既有裁决）

| 裁决/资产 | 如何守住 |
|---|---|
| 宁缺毋滥、不凑数 | 宽通道不设「必发」语义，实发上限不变（maxItems）；填充模式警告照旧 |
| 黑名单一票否决 | 宽通道在预筛前先过黑名单，命中即 drop，测试钉死 |
| 十条终审断言 | 宽通道条目与快通道共用 `finalizeStage` 同一条终审链（wiring 守卫扩到宽路径） |
| LLM 分数不做闸门（DB-04 §六.4） | reviewer 二元判定只做 include/exclude 召回，不产分数进排序，不参与终审判定 |
| jaccard 门禁禁令 | 不引入；事件聚合沿用并查集 |
| 写与评分离 | 宽通道只用 reviewer 链（DeepSeek），不动 writer |
| 探针语域/中文源限制（决策点 4） | 不启用新源；宽通道只作用于现有 13 源 |
| 防回退设计决策 | 事件聚类降权不丢弃、终审前不截断、df 分母=全量——全部不动 |
| 编辑部 calibrate 硬前置 | 宽通道 LLM 判定沿用同一校准体系，未过标不启用 |

## 五、风险与边界

1. **LLM 判定口径漂移**（昨天 calibrate 85.1% 的「质量一致率」不代表「相关判定」准确率）：Phase 2 需对宽通道判定做小标集校准（沿用 gold-standard 派生：DB-03 审计里 200 条可重标「值不值得进」），一致率不足则 `llmGate:'off'` 退回纯启发式。
2. **探针判据语义（重要，需老张拍板）**：判定线 I 线用「相关候选数」做分母/分子（I-1 candidates）；宽召回会抬高相关数口径。若 Phase 2 上线，`gen-evidence`/criteria 需同步口径（或判据记「宽召回版本」），否则 M6 标定回填数据基线可能被污染。**改判据 = 触碰冻结区，属老张签字范围**——这就是为什么 Phase 2 拍板点必须含「判据豁免安排」。
3. **成本**：宽通道每轮 ≤20 条 LLM 判定 × 双 persona ≈ 40 次/轮 × ~30s ≈ 20 分钟增量墙钟（与 writer 并行不叠加）；DS4 双机长期跑着的电力/热量代价需老张知晓（不受控重启循环的根治不在此计划内，plist 已改）。
4. **内容供给的客观波浪**：即使两通道全开，某些时段各源「最新列表」本身就没内容（如非时区发布窗口）——整改目标是「候选池不再因词表恒空」，不是「白天保证 40 条」。诚实口径：允许低产出，不允许词表性零产出。

## 六、实施顺序与拍板点

| # | 拍板点 | 选项 | 建议 |
|---|---|---|---|
| 1 | **Phase 1 止血是否立即做** | 做（词表增补 + 查询串加宽，2-3 个文件，测试约 8-10 例）/ 不做直接跳 Phase 2 | **做**。成本低、可验证、为 Phase 2 提供对照 |
